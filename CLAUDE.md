# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

justbarme is an offline-first PWA for small Nigerian bars ("The Place" is the pilot customer) to record sales, tabs, payments, inventory, and expenses without depending on a live connection. It is a Go modular monolith backed by PostgreSQL, with a React/TypeScript/Vite PWA frontend under `web/` that covers both the public marketing/onboarding site and the authenticated app shell.

Full design decisions live in `docs/`:
- `docs/ARCHITECTURE.md` — the frozen technical architecture (domain model, sync protocol, tenancy, costing, security). Read this before designing any new backend feature.
- `docs/API_CONTRACT.md` — the frozen HTTP/API conventions (envelopes, error codes, config keys, capability names).
- `docs/IMPLEMENTATION_PLAN.md` — the phase-by-phase build plan and the working agreement between the backend owner (this repo's primary author) and the frontend owner (an AI coding agent working in `web/`).

**Current state:** Phase 1 (server lifecycle + health checks), Phase 2 (businesses, memberships, tenancy, authentication), Phase 3's catalogue backend (`internal/catalogue` plus its `internal/httpapi` endpoints), and platform admin oversight (`internal/platformadmin`) are implemented — see the Phase 2, Phase 3, and Platform admin sections below. Sale/bill/payment/inventory/expense modules do not exist yet — do not assume they do until you check `internal/` and `migrations/`. Phase 2 deliberately does **not** include invitations, a `PATCH /business` settings endpoint, or member list/role-management endpoints — those are scheduled for Phase 3+ per `docs/IMPLEMENTATION_PLAN.md`; the only way to create a user today is `cmd/seed` (see below), and the only way to make a second member of a business Staff rather than Owner today is a direct `business_memberships` insert (no invitations endpoint exists yet). Platform admin is not part of the frozen `docs/` plan at all — it was designed and built in-session; see that section for the design rationale before extending it.

## Commands

### Backend (Go, run from repo root)

```
make run          # go run ./cmd/api
make test         # go test ./...
make test-race    # go test -race ./...
make vet          # go vet ./...
make fmt          # gofmt -w on all .go files
make fmt-check    # fails if any file needs gofmt
make benchmark    # go test -run '^$' -bench . -benchmem ./...
make check        # fmt-check + vet + test (run this before calling backend work done)
make tidy         # go mod tidy
```

Single test: `go test ./internal/httpapi/... -run TestName -v`

Requires `JBM_DATABASE_URL` (see `.env.example`) pointing at a real PostgreSQL instance — there is no SQLite fallback, by design (RLS, constraints, and numeric behavior are architectural and must be tested against real PostgreSQL). `internal/store` and `internal/identity` tests call `t.Skip` when `JBM_DATABASE_URL` is unset, so `go test ./...` still passes without a database — but that silently skips the tenant-isolation suite, so always run with a real database before calling backend work on tenancy/auth done. `make test`/`vet`/`fmt-check` intentionally scope to `./cmd/... ./internal/...`, not `./...` — `web/node_modules` can contain vendored `.go` files with no `go.mod` of their own, which `./...` would otherwise pull into this module's build.

**If `JBM_DATABASE_URL` connects as anything other than an actual Postgres superuser** (e.g. a plain role granted `jbm_app` membership rather than the role that originally ran the migrations — a more production-like local setup), most existing test cleanup helpers (`internal/store/tenant_isolation_test.go`, `internal/identity/service_test.go`, `internal/catalogue/service_test.go` as of this writing) **silently stop deleting RLS-scoped rows** (`business_memberships`, `devices`, `locations`, `categories`, `products`, etc.) and leak them into the shared database on every run. They were all written assuming the connecting role bypasses RLS outright, true only for an actual superuser or one with `BYPASSRLS` — a plain raw `DELETE` on a `FORCE ROW LEVEL SECURITY` table under any other role just silently affects zero rows, no error, and the leaked rows then accumulate indefinitely (discovered this way: ~50 leaked test users/businesses after one afternoon's test runs, once `.env` switched to a non-superuser role). `internal/platformadmin/service_test.go`'s `cleanupBusiness` is written the *correct*, role-independent way — it opens a transaction, does `SET LOCAL ROLE jbm_app` and sets `app.business_id` (the same mechanics `store.WithTenant` uses) before deleting from an RLS-scoped table — copy that pattern into the other three files' cleanup helpers before relying on them under a non-superuser `JBM_DATABASE_URL`. If in doubt after a session using such a role, check for leaks directly: `psql "$JBM_DATABASE_URL" -c "select count(*) from users where email like '%@example.com'"` should be zero between sessions.

`.env` (gitignored, real values — `.env.example` is the committed placeholder) is loaded automatically now, two ways: every `make` target sources it via `include .env` + `export` at the top of the Makefile (covers `migrate-*`, which shell out to the external `migrate` CLI and have no other way to see it), and every `cmd/` binary calls `app.LoadDotEnvIfPresent()` (`internal/app/dotenv.go`) as the first thing in `main()`/`run()`, so `go run ./cmd/api` works directly too, not just through `make run`. Neither ever overrides a variable already set in the real environment (CI/production inject `JBM_*` directly and carry no `.env` file, so both are no-ops there), and `config.Load()` itself is unchanged — it still only ever reads `os.Getenv`, per `docs/API_CONTRACT.md` §5's "config is environment-only." **This didn't always exist**: before it did, running a `cmd/` binary directly in a shell that hadn't run `set -a && source .env && set +a` first failed with `invalid configuration: JBM_DATABASE_URL is required` — if you ever see that error, something is bypassing both loading paths (e.g. a test binary, which never calls `main()`; `go test` still needs `.env` sourced manually, or run via `make test`/`make check`).

Two related gotchas, both hit while building the above:
- `internal/app.LoadDotEnvIfPresent`'s parser strips one matching pair of surrounding single/double quotes from a value (`unquote` in `dotenv.go`) — without this, a line like `JBM_DATABASE_URL="postgres://..."` (valid and silently unquoted by a shell's `source`, which is why this went unnoticed for a while) passes the literal quote characters into the value, corrupting it for anything that parses it as a URL.
- Switching `JBM_DATABASE_URL` to a different Postgres role doesn't automatically give that role app access: migration `000001_app_role` only granted `jbm_app` membership to whichever role ran the migrations. A new connecting role needs `GRANT jbm_app TO <role>;` run once, separately, by a privileged role — and that new role still can't run migrations itself unless it also owns the schema (migrations and the app are meant to run as different roles; `jbm_app` is deliberately `NOBYPASSRLS` with no schema-ownership rights, see below).

Migrations (`migrations/`, applied with the `migrate` CLI, not a Go dependency — see `make migrate-up`/`migrate-down`/`migrate-create`) and `internal/store/sqlc` (generated by `sqlc generate` / `make sqlc`, config in `sqlc.yaml`) are the source of truth for the schema — edit `migrations/*.sql` and `internal/store/queries/*.sql`, then regenerate; never hand-edit `internal/store/sqlc/*.sql.go`.

`cmd/seed` bootstraps a user (and optionally a business they own) directly against the database — the only way to create an account today, since invitations aren't built yet: `make seed ARGS="-email=owner@example.com -password='at least 8 chars' -name='Ada Obi' -business='The Place'"`.

`make seed-catalogue` (`cmd/seed-catalogue`) idempotently upserts the platform catalogue templates from `internal/catalogue.NigerianBarCatalogue` — safe to re-run after editing that list, since it upserts by name rather than inserting duplicates.

`make seed-platform-staff` (`cmd/seed-platform-staff`) bootstraps a platform admin account (role `support` or `superadmin`) — the only way to create one, same reasoning as `cmd/seed`: `make seed-platform-staff ARGS="-email=ops@justbarme.example -password='at least 8 chars' -name='Ada Ops' -role=superadmin"`.

## Backend architecture

Composition flows `cmd/api/main.go` (thin entry point, signal handling) → `internal/app.Run` (loads config, opens the PostgreSQL pool, builds the HTTP handler, runs the server with graceful shutdown) → `internal/httpapi.NewHandler` (wires middleware and routes) → `internal/httpapi.NewServer` (the `net/http.Server` with explicit timeouts).

Key conventions, enforced project-wide:

- **`internal/app` is the composition root.** `cmd/api/main.go` must stay minimal — no business logic, no dependency wiring there.
- **Config is environment-only**, prefixed `JBM_`, parsed and validated in `internal/config`. Never hardcode secrets or read config from anywhere else. `config.Load()` fails closed on invalid/missing values — extend `load()` and its `problems` accumulation pattern rather than validating ad hoc elsewhere.
- **HTTP layer uses Chi** (`internal/httpapi/router.go` is the single place routes are registered). Handlers must not contain SQL — they parse/validate transport data and call service-layer code (once feature packages exist under `internal/`).
- **JSON envelope is fixed** (`internal/httpapi/json.go`, `errors.go`): success responses are `{"data": ...}` (optionally `"meta"`), errors are `{"error": {"code", "message", "request_id", "details"}}`. HTTP status is authoritative — never add a redundant `status` field to the JSON body. Use `writeJSON`/`readJSON`/`api.errorResponse` rather than encoding JSON by hand; `readJSON` already enforces `Content-Type: application/json`, unknown-field rejection, single-JSON-value, and body size limits.
- **Every response includes `X-Request-ID`**, sourced from `RequestID(ctx)`; get/propagate it via the existing middleware rather than reinventing request tracing.
- **Liveness never touches the database; readiness always does** (`internal/httpapi/health.go`). Preserve that split when adding new health-adjacent behavior.
- **Money is integer minor units (kobo), never floats.** Quantities are `numeric`/decimal strings, never JSON floats. This applies to both Go and TypeScript.
- **IDs are UUIDv7** via `github.com/google/uuid` (`uuid.NewV7()`), not v4, and never carry presentation prefixes like `usr_`.
- **Timestamps are UTC** (`timestamptz` in PostgreSQL, RFC 3339 in JSON).
- When the domain layer exists: posted financial/inventory records (sales, payments, receipts, expenses) are immutable — corrections are new reversal/replacement events, never `UPDATE`/`DELETE` of history. Tenant-owned tables always carry `business_id` and are accessed through a transaction with `app.business_id` set for RLS; never trust a `business_id` from a request body.
- `internal/validator` is the shared hand-rolled validation helper (`Validator.Check`/`AddError`/`PermittedValue`) — prefer extending it over pulling in a validation library, per `docs/ARCHITECTURE.md`.
- Use `sqlc` for static queries once schema work starts; use direct `pgx` only for genuinely dynamic query shapes (e.g., optional report filters), never by concatenating untrusted strings into SQL.

## Phase 2: tenancy and authentication

Packages added for Phase 2, each matching the layout described in `docs/ARCHITECTURE.md` §4.1:

- `internal/auth` — password hashing (Argon2id, `internal/auth/password.go`, self-describing hash string so cost parameters can change without breaking old hashes), opaque session/CSRF token generation and hashing (`token.go`), the signed offline authorization lease (`lease.go`, Ed25519, a custom compact `v1.<payload>.<signature>` format — not JWT), and a process-local per-key rate limiter (`ratelimit.go`, explicitly not a substitute for distributed rate limiting once more than one instance runs).
- `internal/tenancy` — the fixed Owner/Staff capability map (`capabilities.go`, string constants matching `docs/API_CONTRACT.md` §6 exactly) and the request-scoped `Principal`/`Business` context types (`context.go`). `tenancy.Business.Has(capability)` is how handlers check permissions.
- `internal/identity` — `Service` (`service.go`) wraps users, businesses, memberships, locations, devices, and sessions behind domain types (`model.go`), never exposing generated `sqlc` structs. Every method routes through `internal/store`'s `WithApp`/`WithTenant` transaction helpers — never call `sqlc.New(pool)` directly outside that package.
- `internal/store/tx.go` — `WithApp(ctx, pool, userID, fn)` and `WithTenant(ctx, pool, userID, businessID, fn)` open a transaction, `SET LOCAL ROLE jbm_app` (the reduced-privilege role from `migrations/000001_app_role`, `NOBYPASSRLS`), and `SELECT set_config('app.user_id'/'app.business_id', ..., true)` before running the callback. **Every new tenant-owned query must go through `WithTenant`** — RLS is what actually enforces isolation, not the Go code calling it. Note the `NULLIF(current_setting(...), '')` guard in every RLS policy: a pooled connection can leave a GUC set to `''` (not NULL) from an earlier transaction, which fails a bare `::uuid` cast with a hard error rather than evaluating falsy — see `migrations/000004..006`.
- `internal/httpapi/middleware_auth.go` — `requireAuth` (session cookie → `tenancy.Principal`), `requireCSRF` (same-origin `Origin` + `X-CSRF-Token` hash match, constant-time compare, skipped for safe methods), `requireBusinessContext` (`X-Business-ID` header → verified active membership → `tenancy.Business`; a business that doesn't exist and one the caller isn't a member of both return `404 NOT_FOUND`, deliberately indistinguishable). `requireCapability` is called per-handler, not as middleware, since different routes on the same tenant-scoped group need different capabilities.

Conventions specific to this layer:

- **Never trust a `business_id` in a request body or query string.** The only source of truth is `tenancy.BusinessFromContext`, populated by `requireBusinessContext` after a real membership check.
- **Enrollment vs. administration for devices**: any active member can enroll their *own* device (`POST /devices/enroll`, no capability check beyond active membership — the device's `user_id` is always the caller, never client-supplied); listing or revoking devices requires the owner-only `devices:manage` capability. Apply the same self-service-vs-administration split if a similar pattern comes up elsewhere.
- **Sessions and CSRF tokens are stored only as SHA-256 hashes** (`internal/auth.HashToken`). `GET /api/v1/me` rotates the session's CSRF token on every call (`identity.Service.RotateCSRFToken`) and returns the new raw value — the previous one stops working immediately. Never log a raw session or CSRF token, or a raw offline lease.
- **The offline lease only ever carries `tenancy.OfflineSafe(role)` capabilities** (a fixed subset — see `docs/ARCHITECTURE.md` §11.2), never a role's full capability set, even for an Owner.
- `internal/app/run.go`'s `ensureOfflineSigningKeys` generates an ephemeral Ed25519 keypair when `JBM_OFFLINE_SIGNING_PRIVATE_KEY`/`PUBLIC_KEY` are unset outside production (`config.Load` already refuses to start in production without them) — expected for local dev, but it means every previously issued lease is invalidated on restart unless real keys are configured.

## Phase 3 (backend done; frontend not started): catalogue

`internal/catalogue` (`model.go`, `errors.go`, `convert.go`, `service.go`, `seeddata.go`) implements platform templates, business categories, products, variants, and price history, per `docs/ARCHITECTURE.md` §8.2 and `docs/IMPLEMENTATION_PLAN.md` Phase 3. It follows `internal/identity`'s exact shape (domain types distinct from `sqlc` structs, every method through `store.WithApp`/`WithTenant`). `internal/httpapi/catalogue_handlers.go` and `catalogue_template_handlers.go` wire it to HTTP, tenant-scoped and capability-checked exactly like Phase 2's handlers. None of Phase 3's frontend task list (onboarding using this, product picker, price management UI, offline replicated catalogue storage) is built yet.

- `GET /api/v1/catalogue-templates` needs auth only, no `X-Business-ID` — templates are platform reference data, shown during onboarding before a business necessarily exists. Every other catalogue route is in the `requireBusinessContext` group: `GET/POST /categories`, `PATCH /categories/{id}`, `GET/POST /products`, `GET/PATCH /products/{id}`, `POST /products/{id}/variants`, `PATCH /variants/{id}`, `GET/POST /variants/{id}/prices`, `POST /catalogue-templates/apply`. `GET /products` returns each product with its variants and each variant's current price nested in one response (`catalogue.ProductWithVariants`) — there is deliberately no separate "list variants" endpoint to avoid an N+1 round trip for a catalogue screen.
- **Every mutating catalogue route requires `catalogue:manage` (owner-only); every read route requires only `catalogue:read` (Staff has this too)** — this is what makes the Phase 3 acceptance criterion "Staff can read catalogue but cannot change catalogue/prices" true at the HTTP layer, not just in the capability map. Verified live: a Staff-role session gets `200` on every catalogue `GET` and `403 PERMISSION_DENIED` on every catalogue `POST`/`PATCH` including a price change, and a session scoped to a business the caller isn't a member of gets `404` (via `requireBusinessContext` itself, before any catalogue-specific code runs) rather than seeing another tenant's catalogue.
- `catalogueErrorResponse` in `catalogue_handlers.go` centralizes the `catalogue.Err*` → HTTP status mapping (not-found errors → `404`, name-taken errors → `409`) shared by every category/product/variant handler — extend it there rather than repeating the `errors.Is` chain per handler.

- **Migrations `000008`–`000012`** add `catalogue_templates`/`catalogue_template_variants` (platform-owned, no `business_id`, no RLS — same reasoning as `businesses` itself: nothing ever writes to them through a tenant request path), then the tenant-owned `categories`, `products`, `product_variants`, `product_prices` (all RLS-scoped like every other tenant table). Business branding/settings fields (`phone`, `address`, `receipt_wording`, `receipt_footer`, `payment_instructions`, `logo_object_key`) already existed on `businesses` since Phase 2 — Phase 3's "business branding/settings fields" task needed no new migration, only (eventually) a `PATCH /business` handler, which belongs to the still-unbuilt `internal/business` package per the architecture doc's package layout, not `internal/catalogue`.
- **A variant is never created without a current price.** `Service.CreateVariant` inserts the variant row and its first `product_prices` row in one transaction — there is no code path that produces a priceless variant, which is what makes "exactly one current price per variant" a true invariant from creation onward rather than something callers must remember to establish separately.
- **`Service.SetVariantPrice` closes the old price row and inserts the new one in the same `WithTenant` transaction** — this is the concrete case the project's DB-atomicity rule exists for. A **partial unique index**, `product_prices_one_current_per_variant` (`business_id, variant_id) WHERE valid_to IS NULL`), is the actual enforcement, not the Go code: two concurrent `SetVariantPrice` calls on the same variant can both read the same "current" row before either commits, and only that index — not application logic — stops the loser from inserting a second current row once it wakes from the winner's row lock and its own now-stale `UPDATE ... WHERE valid_to IS NULL` silently matches zero rows. `TestConcurrentSetVariantPriceNeverProducesTwoCurrentPrices` in `internal/catalogue/service_test.go` exercises this directly against real Postgres with two goroutines, not just single-threaded logic — read it before touching this method, since the two legitimate interleavings it accepts (full serialization vs. a genuine conflict-and-rollback) are easy to mistake for a bug if you only think through the single-threaded case.
- **`Service.ApplyTemplates` copies a platform template's product/variants/prices into a business's own catalogue in one transaction**, matching a category by name to an existing business category or creating one (`getOrCreateCategory`) — selecting several templates either all lands or none does; a single unknown template ID rolls the whole selection back (`ErrTemplateNotFound`).
- **Nothing is ever hard-deleted.** `products`, `categories`, and `product_variants` all carry an `active` boolean and expose only `Update*` methods (`UpdateCategory`/`UpdateProduct`/`UpdateVariant`), never a delete query — deactivating is the only removal path, so nothing referencing them (price history, later sales) ever dangles.
- **`Service.SeedTemplates`** upserts by name (`catalogue_templates.name`, `catalogue_template_variants.(template_id, name)` are both `UNIQUE`), so re-running it after editing `NigerianBarCatalogue` in `seeddata.go` is always safe — it is the Phase 3 "repeatable seed mechanism," run via `make seed-catalogue` (`cmd/seed-catalogue`), not a one-shot migration data insert.

## Platform admin

`internal/platformadmin` implements a completely separate identity/authorization space for platform-level operators — people who oversee businesses across the whole service, not members of any one business. This is **not part of `docs/`'s frozen plan**; it was designed and built in-session because there was no provision for it at all (no platform role, no way to suspend an abusive business, no cross-business visibility). Read this whole section before extending it — the design deliberately trades scope for safety in specific places.

**The one rule everything else follows from: no RLS bypass, ever.** The tempting shortcut — a Postgres role with `BYPASSRLS` for admin queries — was rejected: one such role is a single flag that, if any query on it has a bug, exposes every business's data at once, undermining the property (RLS, not application code) that the rest of the system relies on for tenant isolation. Nothing in this v1 slice needs it anyway: `platform_staff`, `platform_sessions`, and `platform_audit_log` (migrations `000013`–`000015`) carry no `business_id` and no RLS at all, same reasoning as `businesses`/`users`; and the one thing platform staff can read across businesses — `ListBusinesses`, via `ListAllBusinesses` — reads only the `businesses` table, which *itself* has never carried RLS (see the Phase 3 note above). Every platform-admin query runs through the ordinary `jbm_app` role via `store.WithApp`, identical to any other non-tenant-scoped read/write elsewhere in the codebase. **Reading a business's actual tenant-owned data (sales, members, catalogue) requires a still-unbuilt, separately audited impersonation flow — do not casually add an RLS policy or a bypass role to make that "convenient" without designing that flow deliberately.**

- **A wholly separate identity space, not a flag on `users`.** `platform_staff`/`platform_sessions` mirror `users`/`sessions` structurally (same case-insensitive email uniqueness, same opaque-token session pattern reusing `internal/auth.HashPassword`/`GenerateToken`/`HashToken` directly) but are different tables entirely, with a different session cookie name (`jbm_platform_session` vs `jbm_session`) and a completely separate context type (`platformStaffContextKey`, never `tenancy.Principal`) in `internal/httpapi`. The intent: a bug in ordinary business-user code can never accidentally grant platform capabilities, and a business session cookie can never be presented as (or confused with) a platform one.
- **Two fixed roles, `support` and `superadmin`** (`internal/platformadmin/capabilities.go`, same `ForRole`-map-not-permission-builder philosophy as `tenancy`). Support has `platform:businesses:read` and `platform:audit:read` only — oversight, never mutation. Only Superadmin has `platform:businesses:suspend`. Enforced the same way as catalogue: `requirePlatformCapability` per handler in `platform_handlers.go`, verified live (a Support session gets `200` reading businesses/audit-log and `403` attempting a suspend).
- **`Service.SuspendBusiness`/`ReactivateBusiness` write the status change and the audit log entry in the same `WithApp` transaction** — the action and its audit trail either both land or neither does, exactly the DB-atomicity pattern used everywhere else in this codebase (see the Phase 3 price-change note above). They just flip `businesses.status`, which already existed since Phase 2.
- **`ListBusinesses` is deliberately not audited**, unlike every mutation. It exposes only non-sensitive summary fields (name, status, timezone, currency, creation date) — nothing tenant-owned. Auditing every read only starts to matter once impersonation (deep, sensitive-data access) exists; do not assume the absence of an audit entry here generalizes to that future feature.
- **`PlatformSession.TTL` defaults to 12 hours** (`JBM_PLATFORM_SESSION_TTL`), deliberately much shorter than a business session's 720 hours — this tier's blast radius if compromised is every business, not one. `platformLoginLimiter` is a separate, tighter rate limiter (5 per 15 minutes vs. business login's 5 per minute) for the same reason. `platformMe` does not rotate its CSRF token on every call the way `GET /me` does, for simplicity — an accepted v1 gap, not a security-equivalent design choice.
- **`cmd/seed-platform-staff`** is the only way to create an account — no signup endpoint, doubly so compared to `cmd/seed`.

## Frontend architecture

`web/` is a single Vite + React + TypeScript + Tailwind v4 PWA that carries **both** the public marketing/onboarding site and the authenticated app shell — there is no separate marketing project. It used to be split across two stacks (this Vite app plus a Next.js prototype in `marketing/`, built from a v0 export template); that Next.js app has been retired and its design system (brand tokens, fonts, and reusable components) ported in here. The v0 template it was originally adapted from is preserved read-only at `agentic-build-and-orchestrate-ai-agents-while-you-sleep/` at the repo root, purely as a design reference — never resurrect a second frontend stack from it.

Routes (`src/app/App.tsx`, `react-router-dom`): `/` (landing page), `/login`, `/onboarding` (4-step wizard — step 1 is a real `POST /businesses`, steps 2-3 are still a UI preview of product/price setup pending Phase 3), `/install` (PWA install guide that performs real device enrollment), `/dashboard` and `/dashboard/sell` (the app shell — auth, business identity and offline-lease status are real; sales/stock figures on the dashboard are still mock data pending later phases). The public pages (`/`, `/login`) need no auth; `/onboarding`, `/install`, `/dashboard*` are wrapped in `RequireAuth`, and the dashboard routes additionally pass `requireBusiness` (see below). The public pages (`/`, `/onboarding`, `/install`) have no offline requirement; only the `/dashboard*` app screens do, per `docs/ARCHITECTURE.md`.

Phase 2 frontend wiring (login, business creation, device enrollment) is real and hits the Go backend:

- `src/lib/session.tsx` — `SessionProvider`/`useSession`: calls `GET /me` on mount, caches the resulting identity in IndexedDB (`src/lib/db.ts`, via Dexie) and falls back to that cache when `/me` fails for a non-401 reason (offline), so a reload while offline doesn't bounce an already-signed-in user to `/login`. A 401 is the only thing that clears the cache and flips to `anonymous`.
- `src/lib/device.ts` — generates and persists a per-device Ed25519 keypair (WebCrypto) in IndexedDB on first use; `src/lib/lease.ts` decodes and verifies a `v1.<payload>.<signature>` offline-authorization lease **entirely client-side** against `VITE_OFFLINE_SIGNING_PUBLIC_KEY`, mirroring `internal/auth.LeasePayload` byte-for-byte. `src/lib/base64.ts` has separate URL-safe/unpadded (`base64UrlEncode/Decode`, matches Go's `RawURLEncoding`) and standard/padded (`base64Encode/Decode`, matches `StdEncoding`) codecs — using the wrong one silently corrupts signature verification.
- `src/components/RequireAuth.tsx` — gates on session `status`; pass `requireBusiness` for any route that assumes a business already exists (currently `/dashboard`, `/dashboard/sell`) so a signed-in user with zero memberships is bounced to `/onboarding` **even if they reach the URL directly** (bookmark, back button, or a stale post-login `from` redirect) rather than only relying on `Login.tsx`'s own post-login routing decision — the two real bugs below are exactly why this exists as a second, independent layer rather than one.

Two non-obvious bugs were found and fixed while wiring this up, verified live against a real `go run ./cmd/api` — both are permanent traps for this exact pattern (auth guard + redirect-back), not one-off mistakes:

1. **Vite's dev `/api` proxy silently breaks the backend's CSRF check.** `internal/httpapi` requires the `Origin` header's host to equal the request's `Host` header (see `middleware_auth.go`'s `requireCSRF`) — correct and sufficient in production, where the frontend and API share one origin. But Vite's dev proxy (`server.proxy`) rewrites the outgoing `Host` header to the proxy target (`localhost:8080`) while the browser's real `Origin` stays `localhost:5173`, so every authenticated `POST`/`PUT`/`PATCH`/`DELETE` in dev gets rejected with `PERMISSION_DENIED` / "not a trusted origin" — confirmed by proxying to a throwaway echo server and inspecting the headers it actually received. Fixed in `vite.config.ts` by re-pinning the proxied request's `Host` header back to the original inbound one via the proxy's `configure`/`proxyReq` hook. If a future upgrade of Vite/its proxy layer changes this default again, this is the symptom to look for.
2. **A same-render state race in `Onboarding.tsx` could bounce a user away from the business they just created.** Creating a business calls `addMembership` (updates `SessionProvider`'s state) and then `setStep(2)` (local state) — two separate `setState` calls separated by an `await`, so React can commit a render in between where `memberships` is already non-empty but `step` is still `1`. The step-1 guard (`memberships.length > 0 && step === 1` → redirect to `/dashboard`, meant only for a returning user who already has a business) fired on that in-between render and skipped straight past product/price setup. Fixed by capturing "did this user already have a business" **once, at mount** (`useState(() => memberships.length > 0)`), not by reading the live `memberships` value in the guard.

Offline-first is the real, load-bearing requirement for the app shell: IndexedDB (via Dexie, once introduced) is meant to be the operational source of truth for business data there, not an in-memory store or query cache. This is also *why* the app was kept on Vite rather than moved to Next.js — Next.js's default rendering mode does per-navigation server round-trips that a service worker cannot cleanly serve from cache, which conflicts with a hard requirement that the app survive an offline reload with pending sales still visible; `output: 'export'` would avoid that but at that point buys nothing Vite doesn't already give more simply.

- `src/styles/global.css` — Tailwind v4 entry point. Brand tokens (`--color-jb-cream`, `--color-jb-ink`, `--color-jb-green`, `--color-jb-green-dark`, `--color-jb-gold`) are defined with **literal values directly in a plain `@theme` block**, not `@theme inline` aliasing a separate `:root` block — that indirection is only needed for tokens that must re-resolve at runtime (e.g. light/dark toggling), which this project doesn't use, and it silently broke Tailwind's utility generation for the bare (non-opacity-suffixed) form of every one of these tokens. Custom base-layer resets (`html`, `body`, `a`, focus rings) are wrapped in `@layer base` — **never leave custom global CSS unlayered** here: an unlayered rule beats every Tailwind utility regardless of specificity, which previously made every `text-*` utility on every `<a>`/`Link` silently no-op in favor of an inherited color. Also: a literal `{ }` pair inside a CSS *comment* was enough to break the Tailwind/Lightning CSS parser with a "Missing opening (" error — keep comments in this file free of brace characters.
- Fonts are self-hosted via `@fontsource` (not Google Fonts CDN) so the app keeps working fully offline: Geist Sans/Mono ship Latin-only already; IBM Plex Sans does not, so it's imported via its `latin-*.css` files specifically (its plain weight files bundle six scripts — cyrillic, greek, vietnamese, etc. — that would otherwise bloat the PWA's precached assets for a Latin-script audience for no benefit).
- `src/components/PixelIcon.tsx`, `RevealText.tsx`, `Logo.tsx`, `PhoneFrame.tsx`, `UiPreviews.tsx`, `MobileNav.tsx`, `AppBottomNav.tsx`, `IntroAnimation.tsx` — the ported design-system components. `PixelIcon` draws to a `<canvas>`; jsdom has no canvas support, so `src/test/setup.ts` logs (harmless) "not implemented" warnings under `vitest` — that's expected, not a bug to fix.
- `src/api/client.ts` — `apiRequest<T>` wraps `fetch`, enforces `credentials: 'same-origin'`, and unwraps the `{data}`/`{error}` envelope into a typed result or a thrown `ApiError`. Route new API calls through this rather than calling `fetch` directly.
- `src/hooks/useConnectivity.ts` — thin `navigator.onLine` wrapper via `useSyncExternalStore`. This is a hint only, per the architecture doc; do not treat it as proof of real connectivity for sync decisions.
- `src/hooks/useServiceHealth.ts` — polls `/api/v1/health/ready` to distinguish `checking`/`available`/`unavailable`/`offline`; surfaced on the dashboard via `StatusBadge`.
- Vite dev server proxies `/api` to `http://localhost:8080` (with the `Host`-header fix above) — run the Go backend alongside `npm run dev` for real API integration. `web/.env` needs `VITE_OFFLINE_SIGNING_PUBLIC_KEY` set to the same value as the backend's `JBM_OFFLINE_SIGNING_PUBLIC_KEY`.
- PWA config (`vite-plugin-pwa` in `vite.config.ts`) explicitly denylists `/api/` from the navigation fallback and starts with no runtime caching — do not cache authenticated API responses in the service worker; persist controlled data in IndexedDB instead, per the architecture doc. App icons are generated from `logo.svg`/`logo.png` at the repo root (`public/icon.svg`, `icon-192.png`, `icon-512.png`) — regenerate the PNGs with `rsvg-convert` (or equivalent) rather than hand-editing them if the mark changes.
- ESLint uses flat config with `typescript-eslint` recommendedTypeChecked plus `react-hooks`/`react-refresh` — `npm run lint` requires zero warnings (`--max-warnings 0`). `tsconfig.app.json` has `noUncheckedIndexedAccess: true`; array-destructured callback params (e.g. an `IntersectionObserver` entry) need an `entry?.` guard, not a bare access.

## Working agreement (from `docs/IMPLEMENTATION_PLAN.md`)

Backend and frontend are treated as separately owned scopes with a phase-gated workflow: each phase has a frozen contract, backend implements it, then frontend implements against the frozen contract. When implementing a phase, stay inside that phase's listed scope — the plan explicitly calls out non-goals per phase (e.g., Phase 1 must not create auth/tenancy/domain packages or `sqlc` output). Check `docs/IMPLEMENTATION_PLAN.md` for the current phase's task list and acceptance criteria before adding new backend packages.
