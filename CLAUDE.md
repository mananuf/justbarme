# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

justbarme is an offline-first PWA for small Nigerian bars ("The Place" is the pilot customer) to record sales, tabs, payments, inventory, and expenses without depending on a live connection. It is a Go modular monolith backed by PostgreSQL, with a React/TypeScript/Vite PWA frontend under `web/` that covers both the public marketing/onboarding site and the authenticated app shell.

Full design decisions live in `docs/`:
- `docs/ARCHITECTURE.md` — the frozen technical architecture (domain model, sync protocol, tenancy, costing, security). Read this before designing any new backend feature.
- `docs/API_CONTRACT.md` — the frozen HTTP/API conventions (envelopes, error codes, config keys, capability names).
- `docs/IMPLEMENTATION_PLAN.md` — the phase-by-phase build plan and the working agreement between the backend owner (this repo's primary author) and the frontend owner (an AI coding agent working in `web/`).

**Current state:** Phase 1 (server lifecycle + health checks), Phase 2 (businesses, memberships, tenancy, authentication), Phase 3's catalogue (`internal/catalogue`, its `internal/httpapi` endpoints — no standalone Settings management page or offline caching yet, see the Phase 3 section), a thin out-of-order slice of Phase 7 stock receiving (`internal/inventory`, `/dashboard/stock`), a single-device slice of Phase 5 walk-in selling (`internal/sales`, `/dashboard/sell`, real offline persistence via IndexedDB — see the Walk-in selling section), a single-device slice of Phase 6 tabs/named credit/payments (also `internal/sales`, `/dashboard/tabs` — online-only, see the Tabs and credit section for why), platform admin oversight (`internal/platformadmin`), public signup (`internal/signup`), Google sign-in (`internal/oauth`), and dual-identity invitations/WhatsApp messaging via Zavu (`internal/whatsapp`, `internal/verification`, `internal/invitations`, `/dashboard/team`) are implemented — see the Phase 2, Phase 3, Stock receiving, Walk-in selling, Tabs and credit, Platform admin, Signup, OAuth, and Invitations and WhatsApp messaging sections below. Onboarding is just business name → done; product/price setup happens the first time an owner logs a stock receipt, not during signup. Phase 4's multi-device sync foundation and expense tracking do not exist yet — do not assume they do until you check `internal/` and `migrations/`. Platform admin, Signup, OAuth, stock receiving/selling/tabs, and invitations/WhatsApp are **not part of the frozen `docs/` plan** (stock receiving, walk-in selling, and tabs are deliberate, documented reorderings ahead of Phase 4 rather than deviations from a specific rule) — read their sections before extending any of them.

## Commands

### Backend (Go, run from repo root)

```
make run          # go run ./cmd/api
make test         # go test ./...
make test-race    # go test -race ./...
make vet          # go vet ./...
make fmt          # gofmt -w on all .go files
make fmt-check    # fails if any file needs gofmt
make benchmark    # go test -run '^$' -bench . -benchmem ./...
make check        # fmt-check + vet + test (run this before calling backend work done)
make tidy         # go mod tidy
```

Single test: `go test ./internal/httpapi/... -run TestName -v`

Requires `JBM_DATABASE_URL` (see `.env.example`) pointing at a real PostgreSQL instance — there is no SQLite fallback, by design (RLS, constraints, and numeric behavior are architectural and must be tested against real PostgreSQL). `internal/store` and `internal/identity` tests call `t.Skip` when `JBM_DATABASE_URL` is unset, so `go test ./...` still passes without a database — but that silently skips the tenant-isolation suite, so always run with a real database before calling backend work on tenancy/auth done. `make test`/`vet`/`fmt-check` intentionally scope to `./cmd/... ./internal/...`, not `./...` — `web/node_modules` can contain vendored `.go` files with no `go.mod` of their own, which `./...` would otherwise pull into this module's build.

**If `JBM_DATABASE_URL` connects as anything other than an actual Postgres superuser** (e.g. a plain role granted `jbm_app` membership rather than the role that originally ran the migrations — a more production-like local setup), most existing test cleanup helpers (`internal/store/tenant_isolation_test.go`, `internal/identity/service_test.go`, `internal/catalogue/service_test.go` as of this writing) **silently stop deleting RLS-scoped rows** (`business_memberships`, `devices`, `locations`, `categories`, `products`, etc.) and leak them into the shared database on every run. They were all written assuming the connecting role bypasses RLS outright, true only for an actual superuser or one with `BYPASSRLS` — a plain raw `DELETE` on a `FORCE ROW LEVEL SECURITY` table under any other role just silently affects zero rows, no error, and the leaked rows then accumulate indefinitely (discovered this way: ~50 leaked test users/businesses after one afternoon's test runs, once `.env` switched to a non-superuser role). `internal/platformadmin/service_test.go`'s `cleanupBusiness` is written the *correct*, role-independent way — it opens a transaction, does `SET LOCAL ROLE jbm_app` and sets `app.business_id` (the same mechanics `store.WithTenant` uses) before deleting from an RLS-scoped table — copy that pattern into the other three files' cleanup helpers before relying on them under a non-superuser `JBM_DATABASE_URL`. If in doubt after a session using such a role, check for leaks directly: `psql "$JBM_DATABASE_URL" -c "select count(*) from users where email like '%@example.com'"` should be zero between sessions.

`.env` (gitignored, real values — `.env.example` is the committed placeholder) is loaded automatically now, two ways: every `make` target sources it via `include .env` + `export` at the top of the Makefile (covers `migrate-*`, which shell out to the external `migrate` CLI and have no other way to see it), and every `cmd/` binary calls `app.LoadDotEnvIfPresent()` (`internal/app/dotenv.go`) as the first thing in `main()`/`run()`, so `go run ./cmd/api` works directly too, not just through `make run`. Neither ever overrides a variable already set in the real environment (CI/production inject `JBM_*` directly and carry no `.env` file, so both are no-ops there), and `config.Load()` itself is unchanged — it still only ever reads `os.Getenv`, per `docs/API_CONTRACT.md` §5's "config is environment-only." **This didn't always exist**: before it did, running a `cmd/` binary directly in a shell that hadn't run `set -a && source .env && set +a` first failed with `invalid configuration: JBM_DATABASE_URL is required` — if you ever see that error, something is bypassing both loading paths (e.g. a test binary, which never calls `main()`; `go test` still needs `.env` sourced manually, or run via `make test`/`make check`).

Two related gotchas, both hit while building the above:
- `internal/app.LoadDotEnvIfPresent`'s parser strips one matching pair of surrounding single/double quotes from a value (`unquote` in `dotenv.go`) — without this, a line like `JBM_DATABASE_URL="postgres://..."` (valid and silently unquoted by a shell's `source`, which is why this went unnoticed for a while) passes the literal quote characters into the value, corrupting it for anything that parses it as a URL.
- Switching `JBM_DATABASE_URL` to a different Postgres role doesn't automatically give that role app access: migration `000001_app_role` only granted `jbm_app` membership to whichever role ran the migrations. A new connecting role needs `GRANT jbm_app TO <role>;` run once, separately, by a privileged role. Whether that new role can *also* run migrations itself depends on the cluster, not on this grant: `jbm_app` itself is deliberately `NOBYPASSRLS` with no schema-ownership rights, but many local Postgres setups still carry the legacy pre-15 default of `CREATE` on the `public` schema granted to `PUBLIC` (every role) — check with `select has_schema_privilege('public', 'public', 'CREATE')` before assuming either way.

Migrations (`migrations/`, applied with the `migrate` CLI, not a Go dependency — see `make migrate-up`/`migrate-down`/`migrate-create`) and `internal/store/sqlc` (generated by `sqlc generate` / `make sqlc`, config in `sqlc.yaml`) are the source of truth for the schema — edit `migrations/*.sql` and `internal/store/queries/*.sql`, then regenerate; never hand-edit `internal/store/sqlc/*.sql.go`.

`cmd/seed` bootstraps a user (and optionally a business they own) directly against the database, bypassing email verification entirely — useful for local dev/test fixtures and the operator's own accounts. A real customer now goes through `POST /auth/signup/start` + `/verify` instead (see the Signup section) — `cmd/seed` is not "the only way" anymore, just the fast, unverified one: `make seed ARGS="-email=owner@example.com -password='at least 8 chars' -name='Ada Obi' -business='The Place'"`.

`make seed-catalogue` (`cmd/seed-catalogue`) idempotently upserts the platform catalogue templates from `internal/catalogue.NigerianBarCatalogue` — safe to re-run after editing that list, since it upserts by name rather than inserting duplicates.

`make seed-platform-staff` (`cmd/seed-platform-staff`) bootstraps a platform admin account (role `support` or `superadmin`) — the only way to create one, same reasoning as `cmd/seed`: `make seed-platform-staff ARGS="-email=ops@justbarme.example -password='at least 8 chars' -name='Ada Ops' -role=superadmin"`.

## Backend architecture

Composition flows `cmd/api/main.go` (thin entry point, signal handling) → `internal/app.Run` (loads config, opens the PostgreSQL pool, builds the HTTP handler, runs the server with graceful shutdown) → `internal/httpapi.NewHandler` (wires middleware and routes) → `internal/httpapi.NewServer` (the `net/http.Server` with explicit timeouts).

Key conventions, enforced project-wide:

- **`internal/app` is the composition root.** `cmd/api/main.go` must stay minimal — no business logic, no dependency wiring there.
- **Config is environment-only**, prefixed `JBM_`, parsed and validated in `internal/config`. Never hardcode secrets or read config from anywhere else. `config.Load()` fails closed on invalid/missing values — extend `load()` and its `problems` accumulation pattern rather than validating ad hoc elsewhere.
- **HTTP layer uses Chi** (`internal/httpapi/router.go` is the single place routes are registered). Handlers must not contain SQL — they parse/validate transport data and call service-layer code (once feature packages exist under `internal/`).
- **JSON envelope is fixed** (`internal/httpapi/json.go`, `errors.go`): success responses are `{"data": ...}` (optionally `"meta"`), errors are `{"error": {"code", "message", "request_id", "details"}}`. HTTP status is authoritative — never add a redundant `status` field to the JSON body. Use `writeJSON`/`readJSON`/`api.errorResponse` rather than encoding JSON by hand; `readJSON` already enforces `Content-Type: application/json`, unknown-field rejection, single-JSON-value, and body size limits.
- **Every response includes `X-Request-ID`**, sourced from `RequestID(ctx)`; get/propagate it via the existing middleware rather than reinventing request tracing.
- **Liveness never touches the database; readiness always does** (`internal/httpapi/health.go`). Preserve that split when adding new health-adjacent behavior.
- **Money is integer minor units (kobo), never floats.** Quantities are `numeric`/decimal strings, never JSON floats. This applies to both Go and TypeScript.
- **IDs are UUIDv7** via `github.com/google/uuid` (`uuid.NewV7()`), not v4, and never carry presentation prefixes like `usr_`.
- **Timestamps are UTC** (`timestamptz` in PostgreSQL, RFC 3339 in JSON).
- When the domain layer exists: posted financial/inventory records (sales, payments, receipts, expenses) are immutable — corrections are new reversal/replacement events, never `UPDATE`/`DELETE` of history. Tenant-owned tables always carry `business_id` and are accessed through a transaction with `app.business_id` set for RLS; never trust a `business_id` from a request body.
- `internal/validator` is the shared hand-rolled validation helper (`Validator.Check`/`AddError`/`PermittedValue`) — prefer extending it over pulling in a validation library, per `docs/ARCHITECTURE.md`.
- Use `sqlc` for static queries once schema work starts; use direct `pgx` only for genuinely dynamic query shapes (e.g., optional report filters), never by concatenating untrusted strings into SQL.

## Phase 2: tenancy and authentication

Packages added for Phase 2, each matching the layout described in `docs/ARCHITECTURE.md` §4.1:

- `internal/auth` — password hashing (Argon2id, `internal/auth/password.go`, self-describing hash string so cost parameters can change without breaking old hashes), opaque session/CSRF token generation and hashing (`token.go`), the signed offline authorization lease (`lease.go`, Ed25519, a custom compact `v1.<payload>.<signature>` format — not JWT), and a process-local per-key rate limiter (`ratelimit.go`, explicitly not a substitute for distributed rate limiting once more than one instance runs).
- `internal/tenancy` — the fixed Owner/Staff capability map (`capabilities.go`, string constants matching `docs/API_CONTRACT.md` §6 exactly) and the request-scoped `Principal`/`Business` context types (`context.go`). `tenancy.Business.Has(capability)` is how handlers check permissions.
- `internal/identity` — `Service` (`service.go`) wraps users, businesses, memberships, locations, devices, and sessions behind domain types (`model.go`), never exposing generated `sqlc` structs. Every method routes through `internal/store`'s `WithApp`/`WithTenant` transaction helpers — never call `sqlc.New(pool)` directly outside that package.
- `internal/store/tx.go` — `WithApp(ctx, pool, userID, fn)` and `WithTenant(ctx, pool, userID, businessID, fn)` open a transaction, `SET LOCAL ROLE jbm_app` (the reduced-privilege role from `migrations/000001_app_role`, `NOBYPASSRLS`), and `SELECT set_config('app.user_id'/'app.business_id', ..., true)` before running the callback. **Every new tenant-owned query must go through `WithTenant`** — RLS is what actually enforces isolation, not the Go code calling it. Note the `NULLIF(current_setting(...), '')` guard in every RLS policy: a pooled connection can leave a GUC set to `''` (not NULL) from an earlier transaction, which fails a bare `::uuid` cast with a hard error rather than evaluating falsy — see `migrations/000004..006`.
- `internal/httpapi/middleware_auth.go` — `requireAuth` (session cookie → `tenancy.Principal`), `requireCSRF` (same-origin `Origin` + `X-CSRF-Token` hash match, constant-time compare, skipped for safe methods), `requireBusinessContext` (`X-Business-ID` header → verified active membership → `tenancy.Business`; a business that doesn't exist and one the caller isn't a member of both return `404 NOT_FOUND`, deliberately indistinguishable). `requireCapability` is called per-handler, not as middleware, since different routes on the same tenant-scoped group need different capabilities.

Conventions specific to this layer:

- **Never trust a `business_id` in a request body or query string.** The only source of truth is `tenancy.BusinessFromContext`, populated by `requireBusinessContext` after a real membership check.
- **Enrollment vs. administration for devices**: any active member can enroll their *own* device (`POST /devices/enroll`, no capability check beyond active membership — the device's `user_id` is always the caller, never client-supplied); listing or revoking devices requires the owner-only `devices:manage` capability. Apply the same self-service-vs-administration split if a similar pattern comes up elsewhere.
- **Sessions and CSRF tokens are stored only as SHA-256 hashes** (`internal/auth.HashToken`). `GET /api/v1/me` rotates the session's CSRF token on every call (`identity.Service.RotateCSRFToken`) and returns the new raw value — the previous one stops working immediately. Never log a raw session or CSRF token, or a raw offline lease.
- **The offline lease only ever carries `tenancy.OfflineSafe(role)` capabilities** (a fixed subset — see `docs/ARCHITECTURE.md` §11.2), never a role's full capability set, even for an Owner.
- `internal/app/run.go`'s `ensureOfflineSigningKeys` generates an ephemeral Ed25519 keypair when `JBM_OFFLINE_SIGNING_PRIVATE_KEY`/`PUBLIC_KEY` are unset outside production (`config.Load` already refuses to start in production without them) — expected for local dev, but it means every previously issued lease is invalidated on restart unless real keys are configured.

## Phase 3: catalogue

`internal/catalogue` (`model.go`, `errors.go`, `convert.go`, `service.go`, `seeddata.go`) implements platform templates, business categories, products, variants, and price history, per `docs/ARCHITECTURE.md` §8.2 and `docs/IMPLEMENTATION_PLAN.md` Phase 3. It follows `internal/identity`'s exact shape (domain types distinct from `sqlc` structs, every method through `store.WithApp`/`WithTenant`). `internal/httpapi/catalogue_handlers.go` and `catalogue_template_handlers.go` wire it to HTTP, tenant-scoped and capability-checked exactly like Phase 2's handlers.

- **`NigerianBarCatalogue` (`seeddata.go`) is 76 templates across four categories** (Beer & Stout, Gin, Whiskey, Spirits — plus the original Soft Drinks and Water), curated from actual Nigerian market research rather than guessed. Entries added after the original seven (Guinness, Star, Heineken, Trophy Lager, Jameson, Hennessy, Gordon's) carry `SuggestedPriceKobo: 0` deliberately — 0 means "no researched estimate, the owner sets the real price during onboarding," not a placeholder to fix later. Re-running `make seed-catalogue` after editing this list is always safe (upserts by name); renaming an entry (e.g. "Trophy" → "Trophy Lager") leaves the old name as an orphaned row that needs a manual one-off `DELETE`, since upsert-by-name has no way to know a rename happened.
- **Onboarding is deliberately just business name → done** (`web/src/pages/Onboarding.tsx`, 2 steps). It used to have search-as-you-type product picking and pricing steps; those were removed in favor of the Stock Receiving section below — see that section for why and for what replaced them. Do not re-add a product/price step to onboarding without re-reading that reasoning first.
- **`web/src/api/catalogue.ts`** is the typed client for `internal/catalogue` — `listProducts`, `applyCatalogueTemplates`, `listCatalogueTemplates`, `createProduct`, `createVariant`, `setVariantPrice` — converting the API's snake_case JSON into camelCase domain objects, same boundary `src/lib/session.tsx` already draws for `/me`. `listProducts`'s response includes a `current_stock` field per variant merged in from `internal/inventory` server-side (see below) — the client type reflects that merge, `internal/catalogue` itself does not.
- **No standalone Settings page for managing the catalogue exists yet** (renaming a product, deactivating something, editing a price outside the stock-receiving flow). `/dashboard/stock` (below) covers adding new products and their initial price; anything beyond that still has no UI. Also not built: offline replicated catalogue storage (IndexedDB caching of `GET /products`) — deferred until something actually needs to read the catalogue offline (Phase 5's Quick Sell screen doesn't exist yet, so nothing does today).

- `GET /api/v1/catalogue-templates` needs auth only, no `X-Business-ID` — templates are platform reference data, shown during onboarding before a business necessarily exists. Every other catalogue route is in the `requireBusinessContext` group: `GET/POST /categories`, `PATCH /categories/{id}`, `GET/POST /products`, `GET/PATCH /products/{id}`, `POST /products/{id}/variants`, `PATCH /variants/{id}`, `GET/POST /variants/{id}/prices`, `POST /catalogue-templates/apply`. `GET /products` returns each product with its variants and each variant's current price nested in one response (`catalogue.ProductWithVariants`) — there is deliberately no separate "list variants" endpoint to avoid an N+1 round trip for a catalogue screen.
- **Every mutating catalogue route requires `catalogue:manage` (owner-only); every read route requires only `catalogue:read` (Staff has this too)** — this is what makes the Phase 3 acceptance criterion "Staff can read catalogue but cannot change catalogue/prices" true at the HTTP layer, not just in the capability map. Verified live: a Staff-role session gets `200` on every catalogue `GET` and `403 PERMISSION_DENIED` on every catalogue `POST`/`PATCH` including a price change, and a session scoped to a business the caller isn't a member of gets `404` (via `requireBusinessContext` itself, before any catalogue-specific code runs) rather than seeing another tenant's catalogue.
- `catalogueErrorResponse` in `catalogue_handlers.go` centralizes the `catalogue.Err*` → HTTP status mapping (not-found errors → `404`, name-taken errors → `409`) shared by every category/product/variant handler — extend it there rather than repeating the `errors.Is` chain per handler.

- **Migrations `000008`–`000012`** add `catalogue_templates`/`catalogue_template_variants` (platform-owned, no `business_id`, no RLS — same reasoning as `businesses` itself: nothing ever writes to them through a tenant request path), then the tenant-owned `categories`, `products`, `product_variants`, `product_prices` (all RLS-scoped like every other tenant table). Business branding/settings fields (`phone`, `address`, `receipt_wording`, `receipt_footer`, `payment_instructions`, `logo_object_key`) already existed on `businesses` since Phase 2 — Phase 3's "business branding/settings fields" task needed no new migration, only (eventually) a `PATCH /business` handler, which belongs to the still-unbuilt `internal/business` package per the architecture doc's package layout, not `internal/catalogue`.
- **A variant is never created without a current price.** `Service.CreateVariant` inserts the variant row and its first `product_prices` row in one transaction — there is no code path that produces a priceless variant, which is what makes "exactly one current price per variant" a true invariant from creation onward rather than something callers must remember to establish separately.
- **`Service.SetVariantPrice` closes the old price row and inserts the new one in the same `WithTenant` transaction** — this is the concrete case the project's DB-atomicity rule exists for. A **partial unique index**, `product_prices_one_current_per_variant` (`business_id, variant_id) WHERE valid_to IS NULL`), is the actual enforcement, not the Go code: two concurrent `SetVariantPrice` calls on the same variant can both read the same "current" row before either commits, and only that index — not application logic — stops the loser from inserting a second current row once it wakes from the winner's row lock and its own now-stale `UPDATE ... WHERE valid_to IS NULL` silently matches zero rows. `TestConcurrentSetVariantPriceNeverProducesTwoCurrentPrices` in `internal/catalogue/service_test.go` exercises this directly against real Postgres with two goroutines, not just single-threaded logic — read it before touching this method, since the two legitimate interleavings it accepts (full serialization vs. a genuine conflict-and-rollback) are easy to mistake for a bug if you only think through the single-threaded case.
- **`Service.ApplyTemplates` copies a platform template's product/variants/prices into a business's own catalogue in one transaction**, matching a category by name to an existing business category or creating one (`getOrCreateCategory`) — selecting several templates either all lands or none does; a single unknown template ID rolls the whole selection back (`ErrTemplateNotFound`).
- **Nothing is ever hard-deleted.** `products`, `categories`, and `product_variants` all carry an `active` boolean and expose only `Update*` methods (`UpdateCategory`/`UpdateProduct`/`UpdateVariant`), never a delete query — deactivating is the only removal path, so nothing referencing them (price history, later sales) ever dangles.
- **`Service.SeedTemplates`** upserts by name (`catalogue_templates.name`, `catalogue_template_variants.(template_id, name)` are both `UNIQUE`), so re-running it after editing `NigerianBarCatalogue` in `seeddata.go` is always safe — it is the Phase 3 "repeatable seed mechanism," run via `make seed-catalogue` (`cmd/seed-catalogue`), not a one-shot migration data insert.

## Stock receiving

`internal/inventory` implements stock receiving — a deliberately thin slice of `docs/ARCHITECTURE.md` §8.4's full inventory model, pulled forward ahead of the frozen phase order (full inventory is Phase 7, scheduled after sync/selling/tabs). See `docs/PHASE_STOCK_RECEIVING.md` for the full reasoning and explicit non-goals (no counts, staff adjustment approvals, negative-inventory reviews, or FIFO cost allocation yet — none of those need to exist for one owner receiving stock).

- **This is why onboarding no longer has product/price steps.** The first real stock receipt an owner logs — "I bought 48 bottles of Trophy Lager for ₦43,000" — is what gives their catalogue its first entry, via `/dashboard/stock`, not a mandatory signup step. Onboarding is just business name → done.
- **Migration `000018`** adds `stock_receipts` (header), `stock_receipt_lines` (one row per variant in a receipt: quantity + total cost), `stock_lots` (one immutable costed lot per line, duplicating the line today since nothing consumes lots yet — kept as its own table specifically so a future FIFO allocator, Phase 10, doesn't need a schema redesign), `inventory_events` (operation headers, `type` `CHECK`-constrained to `'receipt'` only for now), `inventory_movements` (append-only signed quantity deltas), and `inventory_balances` (the rebuildable projection actually read for display). Same tenant-isolation pattern as every other RLS-scoped table in this codebase — composite FKs, `FORCE ROW LEVEL SECURITY`, `NULLIF(current_setting(...), '')::uuid` policies.
- **Store the total, never a rounded per-unit cost.** `docs/ARCHITECTURE.md` §8.4 is explicit about this: a receipt line is quantity + total cost, and per-bottle cost is always computed at display time (`total ÷ quantity`), never stored — repeated rounding across many receipts would otherwise silently drift from the truth. This is also why "4 crates × 12 bottles at ₦43,000 total" and "1 crate of 12 at ₦8,750" are the same shape: one line each, `quantity = crates × bottles-per-crate`.
- **`Service.ReceiveStock` posts a receipt header, its lines, their lots, one `inventory_events` row, and one `inventory_movements` + `inventory_balances` increment per line, all in a single transaction** — the same non-negotiable atomicity pattern as `catalogue.Service.SetVariantPrice`/`platformadmin.Service.SuspendBusiness`. It returns each line's resulting balance (`NewBalance`) captured from the same transaction's balance-upsert `RETURNING`, not a separate read, so it can never reflect a concurrent receipt landing in between.
- **`internal/inventory` does not depend on `internal/identity` or `internal/catalogue`**, per the project's "each feature package stays self-contained" rule. The HTTP handler (`receiveStock` in `internal/httpapi/inventory_handlers.go`) resolves the receiving location itself via `identity.Service.GetDefaultLocation` and passes it in — the client never sends a `location_id`, since multi-location isn't a pilot concern even though every table carries the column. Similarly, `GET /api/v1/products`'s handler merges `inventory.Service.GetBalances` into the existing catalogue response (`current_stock` per variant) rather than `internal/catalogue` knowing inventory exists.
- **Capability names (`inventory:receive`, `inventory:read`) already existed** in `internal/tenancy/capabilities.go` before this feature was built — the architecture anticipated this. `inventory:receive` is Owner-only for now (the existing capability-map comment already flagged Staff receiving as "a pilot observation," unconfirmed); `inventory:read` is both Owner and Staff.
- **Frontend**: `/dashboard/stock` (`web/src/pages/Stock.tsx`), replacing the dead `#stock` anchor `AppBottomNav` had reserved since before this feature existed. One flow: search your own products or the platform catalogue (or type something not found in either as a new custom product, defaulting its one variant's name to "Bottle" rather than asking — one field, not two); a selling price is asked once, only the first time a product is created, never on a routine restock; then a Crate/Bottle toggle with a live "≈ ₦X/bottle" preview that is never itself submitted, only the total cost is. Bottles-per-crate is remembered per variant in `localStorage` (`src/lib/stockPreferences.ts`, same per-device-only reasoning as the dashboard tour's "seen" flag) so restocking the same product doesn't require retyping it.
- **Verified live end-to-end** against a running backend before this was considered done: applied a template, posted the exact "4 crates × 12 at ₦43,000" receipt via curl, confirmed `GET /products` reflected the new `current_stock`, and separately confirmed the custom-product path (`POST /products` → `POST /products/{id}/variants`) matches the frontend client's expected shape. Test data cleaned up afterward.

## Walk-in selling

`internal/sales` implements Phase 5 (walk-in selling), also built as a single-device slice — Phase 4's multi-device sync foundation is explicitly deferred until invitations bring a second device into a real business (recorded in this session's project memory; re-check that decision before building anything that assumes Phase 4 exists). `Sell.tsx` was a complete UI mock before this — hardcoded products, fake prices, a "will sync automatically" message backed by nothing — all of that is now real.

- **Migration `000019`** adds `bills`, `sales`, `sale_items`, `payments`, and `sale_reviews`, and widens `inventory_events.type`'s `CHECK` from `('receipt')` to `('receipt', 'sale', 'sale_reversal')` — the same one-migration-per-addition discipline `000018` established. Only the walk-in-relevant bill statuses exist (`open`, `settled`) — tabs (`closed_unpaid`, `void`, `tables`, `customers`) are Phase 6, not built.
- **`sales.total_kobo` is `SUM(sale_items.line_total_kobo)`, sign and all — never a separately-asserted magnitude.** An ordinary sale's items all have positive quantity, so its total is positive; a reversal's compensating items are all negative, so its total is negative. This is what makes `SumSalesTotalSince` a plain `SUM(total_kobo)` with no `CASE WHEN` for reversals — the sign already carries the meaning. Line/unit costs still never go negative independently; only `quantity` (and therefore `line_total_kobo`) flips sign for a reversal.
- **`Service.CreateSale` resolves everything (variant lookups, staleness checks, the running total) *before* creating the `sales` row, then creates every child row after** — `sale_items`, `inventory_events`, and `sale_reviews` all carry a foreign key back to `sales`, so that row has to exist first, which means its total has to be known first. Getting this ordering backwards is an easy, silent-until-tested mistake (it was made and caught by this feature's own tests during development, not left as a landmine) — read this method before changing the write order.
- **Idempotency is real, not decorative.** `sales.idempotency_key` is client-generated (a UUID minted on-device the moment "Complete Sale" is tapped) and unique per business. `CreateSale` checks for an existing row with that key *first*, inside the same transaction, before doing any other work — a retried POST (lost response, offline retry) returns the sale already posted the first time rather than creating a second one or erroring. `TestCreateSaleIsIdempotent` exercises this directly.
- **A sale is never rejected for a deactivated variant or a stale price — it always posts exactly as submitted**, and a `sale_reviews` row opens instead, for the owner to look at later (never a reason to alter the sale). This is deliberately a narrow, sale-specific table, *not* the generic, multi-purpose `review_cases` system `docs/IMPLEMENTATION_PLAN.md`'s Phase 4 describes (that one also covers stock counts and adjustments, neither of which exist yet). Only a genuinely nonexistent `variant_id` is rejected (`ErrVariantNotFound`) — that's a malformed request, not staleness.
- **`Service.ReverseSale` creates new, equal-and-opposite rows — it never edits or deletes the original.** A second `sales` row (`reversal_of_sale_id` pointing back), negative-quantity `sale_items` copying the original lines, positive inventory movements that put the stock back, and a negative-amount `payments` row (a refund). `GetReversalOfSale` enforces at most one reversal per sale (`ErrAlreadyReversed`). The reversal restocks at the *original sale's own location* (fetched via the bill it belongs to), not whatever the caller's current default location happens to be — those are the same thing today (single location per business) but the distinction is the right one to keep.
- **Capabilities (`sales:record`, `sales:reverse`) already existed** in `internal/tenancy/capabilities.go`. `sales:record` is both Owner and Staff; `sales:reverse` (and, by reuse, resolving a review) is Owner-only. Listing sales/reviews and the summary endpoint use `activity:read`/`reports:read` respectively — both Owner-only today, so whether Staff should see their own sales history is an open pilot question, the same shape as `inventory:receive`'s already-flagged Staff ambiguity.
- **`GET /api/v1/sales/summary` computes "today" in the business's own timezone** (`businesses.timezone`), not the server's or the browser's — a sale just before local midnight is never misattributed to the wrong day. Its `today_sale_count` deliberately excludes reversals (a correction isn't "one more sale" for display purposes) while `today_total_kobo` still nets them in.
- **Frontend offline persistence is now real**, via a new Dexie table (`pendingSales` in `src/lib/db.ts`, version 2). Completing a sale writes to IndexedDB *first*, before any network call — that write is what "Sale recorded" now actually means, not a message with nothing behind it. `src/lib/salesSync.ts`'s `flushPendingSales` posts any still-pending sale to the server, oldest first, stopping at the first failure rather than reordering; it runs on `Sell.tsx` mount, on regaining connectivity (`useConnectivity`), and right after a new sale queues. This is single-device offline support, not Phase 4's multi-device sync — deliberately kept simple (no background-sync-while-closed, no conflict resolution) since neither is needed yet.
- **`Sell.tsx`'s product grid now reads real, active variants** from `GET /products` (via `listProducts`, already built for Phase 3) instead of a hardcoded list — filtered on `active` (a field `web/src/api/catalogue.ts`'s `CatalogueVariant` didn't carry until this phase needed it).
- **Dashboard's "Today's Sales" and "Recent Activity" are wired to `GET /sales/summary` and `GET /sales`** — the three other mock stats that used to sit next to "Today's Sales" (items sold, expenses, tabs) were removed rather than left half-real, since none of those modules exist yet. "Stock alerts" and "Outstanding" (tabs) remain mock — inventory low-stock thresholds have no backend concept yet, and although real outstanding-balance data now exists (Phase 6's `GET /bills?status=outstanding`), `Dashboard.tsx` itself was not touched to wire it in; that's still a real gap, not done implicitly by Phase 6 existing.
- **Recent Activity shows who recorded each sale** ("Ada recorded a sale" / "Ada reversed a sale") — `listSales`'s handler resolves `seller_name` via the same `resolveSellerNames` helper the Tabs and credit section describes, so this and the bill-detail rounds view share one seller-name-resolution mechanism rather than two. **The greeting is time-of-day-based** (`timeBasedGreeting()` in `Dashboard.tsx`, using the device's own local hour via `new Date().getHours()` — a cosmetic greeting has no need for the business-timezone precision `GET /sales/summary`'s "today" boundary requires), not the permanently-hardcoded "Good evening" it shipped with. `App.test.tsx`'s two dashboard-rendering tests that assert on `/good evening/i` now pin the clock with `vi.setSystemTime(...)` first — without that they'd only pass between 17:00 and midnight, whatever timezone the test runner resolves `Date()` in.
- **Verified live end-to-end** against a running backend: a real sale posted and deducted stock, a retried POST with the same idempotency key returned the identical sale without double-deducting, a price-mismatch sale opened and then resolved a review, and a reversal exactly negated the original (stock restored, payment refunded, double-reversal rejected with `409`). The frontend's own IndexedDB queueing path (`Sell.tsx`/`salesSync.ts`) was not driven through a real browser as part of this pass — only the backend it talks to was live-verified — so it's worth a manual pass (or Playwright) before trusting it in production, the same caveat OAuth's frontend carries.

## Tabs and credit

`internal/sales` widens further for Phase 6 (tables, customers, and the full bill lifecycle: opening a tab, appending rounds, partial payments, reversal, owner-only write-off, close/settle/void) — the same single-device-slice reasoning as Phase 5, explicitly reconfirmed rather than assumed when this phase started. See [`PHASE_TABS_CREDIT.md`](docs/PHASE_TABS_CREDIT.md) for full reasoning, schema, and the live-verification transcript (including the Staff/Owner permission split). Read it before extending any bill/payment/table/customer code.

- **Unlike Phase 5, this frontend slice is deliberately online-only** — `Tabs.tsx` calls the API directly with no IndexedDB outbox, since a tab is touched by several separate operations over time (not one atomic action) and building that correctly overlaps heavily with what Phase 4 exists to solve. This is a real, named scope narrowing, not an oversight — see the doc's "What's different from Phase 5" section before assuming tabs get the same offline treatment sales do.
- **`bills.balance_kobo` is a rebuildable projection** (`sales` totals minus `payments` minus `bill_write_offs`, recomputed and persisted by `internal/sales.recomputeBillBalance` inside the same row-locked transaction as every bill-mutating call), the same pattern `inventory_balances` already established. Every such method takes the bill's row lock (`GetBillForUpdate`) first — `TestConcurrentPaymentsNeverExceedBalance` (`internal/sales/tabs_test.go`) exercises two goroutines racing to pay off the same bill to confirm this actually serializes them.
- **`AppBottomNav`'s "Bills" tab now points at the real `/dashboard/tabs` route** instead of the dead `#bills` anchor it used to reserve.
- Fixed in passing: a pre-existing bug in `internal/sales/service_test.go`'s cleanup helper (deleting `sales` before `inventory_events`, whose `sale_id` FK — added by Phase 5's own migration — blocks that order) that had been silently leaking every sales test's rows under a non-superuser `JBM_DATABASE_URL` since Phase 5 was built.
- **Orders on an `open`/`closed_unpaid` bill are correctable in place** — `AddSaleRound` ("+") and the newer `RemoveBillItem` ("−", a compensating negative round, capped by `SumBillItemQuantityByVariant`) both post immediately from `Tabs.tsx`'s live-aggregated "current order" stepper, never editing a previously posted round. Once a bill is `settled`/`void` this is rejected (`ErrBillNotEditable`) — correcting a fully paid bill needs a per-bill-aware reversal that doesn't exist yet (`ReverseSale` always opens a disconnected new bill, wrong for a shared tab) — see `docs/PHASE_TABS_CREDIT.md`'s "Editable orders" section before building that.
- **Each round in a bill's "ROUNDS" history shows who recorded it** — `sales.seller_id` already existed on every `Sale`; this was a display gap, closed once invitations meant more than one staff member genuinely touches the same tab. `saleResponse.seller_id` is always populated (free — already on the domain struct); `seller_name` is resolved via `resolveSellerNames` (`internal/httpapi/tabs_handlers.go`, deduping by seller before calling `identity.Service.GetUserByID` so cost scales with distinct staff on the bill/list, not row count) on both `getBillDetail` and `listSales` — the latter is what Dashboard's Recent Activity reads (see the Walk-in selling section). No *other* sale-returning endpoint populates it (`createSale`/`addSaleRound`/`removeBillItem`/`reverseSale` all leave it empty), since every caller of those already re-fetches full bill detail or the sales list right after anyway. See `docs/PHASE_TABS_CREDIT.md`'s "Seller attribution on rounds" section.

## Platform admin

`internal/platformadmin` implements a completely separate identity/authorization space for platform-level operators — people who oversee businesses across the whole service, not members of any one business. This is **not part of `docs/`'s frozen plan**; it was designed and built in-session because there was no provision for it at all (no platform role, no way to suspend an abusive business, no cross-business visibility). Read this whole section before extending it — the design deliberately trades scope for safety in specific places.

**The one rule everything else follows from: no RLS bypass, ever.** The tempting shortcut — a Postgres role with `BYPASSRLS` for admin queries — was rejected: one such role is a single flag that, if any query on it has a bug, exposes every business's data at once, undermining the property (RLS, not application code) that the rest of the system relies on for tenant isolation. Nothing in this v1 slice needs it anyway: `platform_staff`, `platform_sessions`, and `platform_audit_log` (migrations `000013`–`000015`) carry no `business_id` and no RLS at all, same reasoning as `businesses`/`users`; and the one thing platform staff can read across businesses — `ListBusinesses`, via `ListAllBusinesses` — reads only the `businesses` table, which *itself* has never carried RLS (see the Phase 3 note above). Every platform-admin query runs through the ordinary `jbm_app` role via `store.WithApp`, identical to any other non-tenant-scoped read/write elsewhere in the codebase. **Reading a business's actual tenant-owned data (sales, members, catalogue) requires a still-unbuilt, separately audited impersonation flow — do not casually add an RLS policy or a bypass role to make that "convenient" without designing that flow deliberately.**

- **A wholly separate identity space, not a flag on `users`.** `platform_staff`/`platform_sessions` mirror `users`/`sessions` structurally (same case-insensitive email uniqueness, same opaque-token session pattern reusing `internal/auth.HashPassword`/`GenerateToken`/`HashToken` directly) but are different tables entirely, with a different session cookie name (`jbm_platform_session` vs `jbm_session`) and a completely separate context type (`platformStaffContextKey`, never `tenancy.Principal`) in `internal/httpapi`. The intent: a bug in ordinary business-user code can never accidentally grant platform capabilities, and a business session cookie can never be presented as (or confused with) a platform one.
- **Two fixed roles, `support` and `superadmin`** (`internal/platformadmin/capabilities.go`, same `ForRole`-map-not-permission-builder philosophy as `tenancy`). Support has `platform:businesses:read` and `platform:audit:read` only — oversight, never mutation. Only Superadmin has `platform:businesses:suspend`. Enforced the same way as catalogue: `requirePlatformCapability` per handler in `platform_handlers.go`, verified live (a Support session gets `200` reading businesses/audit-log and `403` attempting a suspend).
- **`Service.SuspendBusiness`/`ReactivateBusiness` write the status change and the audit log entry in the same `WithApp` transaction** — the action and its audit trail either both land or neither does, exactly the DB-atomicity pattern used everywhere else in this codebase (see the Phase 3 price-change note above). They just flip `businesses.status`, which already existed since Phase 2.
- **`ListBusinesses` is deliberately not audited**, unlike every mutation. It exposes only non-sensitive summary fields (name, status, timezone, currency, creation date) — nothing tenant-owned. Auditing every read only starts to matter once impersonation (deep, sensitive-data access) exists; do not assume the absence of an audit entry here generalizes to that future feature.
- **`PlatformSession.TTL` defaults to 12 hours** (`JBM_PLATFORM_SESSION_TTL`), deliberately much shorter than a business session's 720 hours — this tier's blast radius if compromised is every business, not one. `platformLoginLimiter` is a separate, tighter rate limiter (5 per 15 minutes vs. business login's 5 per minute) for the same reason. `platformMe` rotates its CSRF token on every call, same as `GET /me` (`Service.RotateCSRFToken`) — without it, a reloaded platform admin page would have no way to obtain a usable token (only its hash is ever stored) and every mutating request would fail until re-login.
- **`cmd/seed-platform-staff`** is the only way to create an account — no signup endpoint, doubly so compared to `cmd/seed`.

Frontend: `src/lib/platformSession.tsx` (`PlatformSessionProvider`/`usePlatformSession`), `src/components/RequirePlatformAuth.tsx`, and `src/pages/platform/{PlatformLogin,PlatformDashboard}.tsx` — a wholly separate route tree in `App.tsx` (`/platform/login`, `/platform`), wrapped in its own `PlatformSessionProvider` via a layout route (`<Route element={<PlatformSessionProvider><Outlet /></PlatformSessionProvider>}>`), never nested inside the business `SessionProvider`. No IndexedDB caching here (unlike `session.tsx`) — this is an always-online ops tool with no offline requirement, so a failed `/platform/me` just means "not signed in," no cached-identity fallback needed. `PlatformDashboard` lists every business with a Suspend/Reactivate button shown only when `staff.role === 'superadmin'` (Support sees the same list read-only, matching the backend capability split) and a collapsible recent-activity panel reading the audit log. Verified live end-to-end with Playwright, including that a mutation performed *after* a page reload still succeeds — that specifically exercises the `platformMe` CSRF-rotation fix above, not just the token issued at login.

## Signup

`internal/signup` implements public account signup with email-code verification: anyone can create their own account and business, no invitation required. This is a **deliberate deviation from `docs/ARCHITECTURE.md` §11.1**, which says *"for the pilot, support invited accounts using normalized email plus password"* — there was and is no documented design for open signup; this was designed and confirmed in-session (see the conversation that led here for the reasoning), not derived from `docs/`. The email-OTP mechanism itself is also a deviation from §11.1's *"SMS OTP adds cost and delivery complexity and is deferred"* — that line is about SMS specifically; email OTP was chosen deliberately for this audience (mobile-first bar owners who may check email in a different app/context than where they started signup, where a click-through link is more likely to break the flow than a typed code).

- **Two-step flow, one continuous UX**: `POST /auth/signup/start` (email, name, password) hashes the password immediately and emails a 6-digit code — nothing in `users` exists yet. `POST /auth/signup/verify` (email, code) is what actually creates the `users` row and a real session, in the same shape as `POST /auth/login`'s response, so the frontend reuses one code path (`useSession().verifySignup` calls the same internal `applyMe` `login` does). There is no separate "resend" endpoint — calling `start` again for the same email just replaces the pending code (`signup_verifications` is upserted by `lower(email)`, `Attempts` reset to 0).
- **Nothing pending ever touches `users.email`'s uniqueness.** `signup_verifications` (migration `000016`, no RLS — not tenant-owned, same reasoning as `users`/`platform_staff`) holds the hashed password and hashed OTP for an unverified signup; the real `users` row is only created inside `Verify`, via `identity.Service.CreateUserWithHashedPassword` (a sibling of `CreateUser` that skips re-hashing, since the password was already hashed at `Start` — a plaintext password is never held in memory across the wait for a code).
- **Signup discloses whether an email is already registered** (`ErrEmailAlreadyRegistered` → `409 EMAIL_ALREADY_REGISTERED`, "This email is already registered. Sign in instead.") — a deliberate choice, the opposite of login's "one generic invalid-credentials response, do not reveal whether an email exists" from `docs/API_CONTRACT.md` §8. Confirmed in-session: signup conventionally tells the truth here so a returning owner isn't stuck. `identity.Service.EmailIsRegistered` is the minimal check this needed — a boolean, not a full `User` lookup, kept out of `internal/signup`'s own reach into `users`.
- **A 6-digit code is only as safe as the limits around it.** Three layers, all defense-in-depth, none alone sufficient: `signup_verifications.attempts` (locks a specific pending signup out after `internal/signup.maxOTPAttempts` = 5 wrong tries, checked inside `Verify` itself, even before time-expiry), plus two `auth.Limiter` pairs in `router.go` — `signupStartEmailLimiter`/`signupStartIPLimiter` (3/hour per email, 10/hour per IP — this endpoint sends real email and creates DB rows, a more attractive target than login) and `signupVerifyEmailLimiter`/`signupVerifyIPLimiter` (10 and 30 per 15 minutes) guarding brute-force attempts across many emails or from many sources.
- **`internal/email`** is the transactional-email boundary `docs/ARCHITECTURE.md`'s diagrams always showed but never built (`API --> Email[Email provider]`), kept behind a `Provider` interface per `docs/IMPLEMENTATION_PLAN.md`'s explicit instruction ("keep provider behind an interface"). `SMTPProvider` is a plain `net/smtp` client (STARTTLS, explicit dial timeout since `net/smtp` has no context support) — the pilot points it at Gmail's relay with an app password, but nothing in it is Gmail-specific. `ConsoleProvider` just logs the message instead of sending it, used automatically outside production when `JBM_SMTP_USERNAME`/`PASSWORD`/`FROM` aren't set (`config.SMTP.Configured()`) — same dev-convenience-not-silent-gap pattern as `ensureOfflineSigningKeys`; `config.Load` refuses to start in production without real SMTP credentials.
- **Every transactional email is a real HTML design, not plain text** — added during the Invitations and WhatsApp messaging phase after a real invitation email was reported looking so bare it landed in spam. `Message.HTML` is optional (`""` means text-only, unchanged behavior); `NewHTMLTemplate`/`MustNewHTMLTemplate` (`internal/email/template.go`) sit alongside the original `NewTemplate`/`MustNewTemplate` rather than replacing them. `Layout`/`MustLayout` (`internal/email/layout.go`) is the one shared HTML shell — dark header band with the wordmark, cream content card, muted footer, colors kept in sync **by hand** with `web/src/styles/global.css`'s `--color-jb-*` tokens since an email client can't read a CSS file — every feature package's own content (`internal/signup`/`internal/verification`'s OTP emails, `internal/invitations`' invite email) renders inside it, table-based markup with inline styles throughout (the lowest common denominator across email clients, not ported from the web app's Tailwind classes). `SMTPProvider.buildMessage` sends a real `multipart/alternative` message (plain-text part first, HTML last, per RFC 2046) whenever `Message.HTML` is set, and the original plain-text-only format otherwise — `ConsoleProvider` just logs whether `has_html` is true, same as everything else it logs. A neat trick worth reusing for a quick design check without spending real signups: `NewHTMLTemplate`'s `htmlSrc` argument is itself the *output* of `Layout`, which contains still-unexecuted `{{ }}` placeholders (e.g. `{{.Code}}`) baked in as literal text — Go's `text/template` never recursively re-parses its own output, so this two-phase build (wrap once at package-init, execute per-send with real data) works cleanly. The header band and footer also carry the actual brand mark now, not just the text wordmark — `logoPathData` in `layout.go` is `web/src/components/Logo.tsx`'s own SVG path copied in by hand (email has no build step to share a frontend component through), inlined as `<svg>` at header size (gold, beside "JUSTBARME") and footer size (muted, above the tagline); a client that can't render inline SVG at all (chiefly Outlook desktop) just shows neither and the text next to it still reads fine, an acceptable degradation. `s.otpTTL`/`otpTTL`'s value going into an OTP message's `{{.ExpiresIn}}` is formatted by each package's own `humanDuration` helper ("10 minutes"), never Go's raw `time.Duration.String()` ("10m0s") — that raw form shipped briefly and read like a bug to an actual recipient.
- **`email.WithRetry` wraps a `Provider` with exponential-backoff retry** — a `Provider` decorator, not a special case inside `SMTPProvider`, so it composes with any implementation. `internal/app.emailProvider` applies it only to the real `SMTPProvider` (`ConsoleProvider` can never fail, so wrapping it would just be dead code exercised on every call): 3 attempts total by default (`JBM_SMTP_MAX_SEND_ATTEMPTS`, `config.SMTP.MaxSendAttempts`), backoff doubling from 500ms (`JBM_SMTP_RETRY_BASE_DELAY`, `config.SMTP.RetryBaseDelay`). It respects context cancellation mid-backoff rather than sleeping through it. `internal/signup.Service.Start` returning an error (and thus the whole signup attempt failing) after 3 failed sends is the intended behavior for a relay that's genuinely down — there is deliberately no background/async retry queue for this v1 slice.
- **`email.Template`/`NewTemplate`/`MustNewTemplate` is the one place any email's Subject/Text gets built**, via `text/template` rather than ad hoc `fmt.Sprintf` per caller — this is what makes the `Provider` interface "flexible for any kind of email," not just OTP codes. Each feature package defines its own templates at package-init time (`internal/signup`'s `otpEmailTemplate`, parsed once so a malformed template is a startup-time panic via `MustNewTemplate`, never something a live request can trigger) and its own small data struct to render against — `internal/email` itself stays generic and knows nothing about signup, receipts, or any other specific email content.
- **Frontend**: `src/pages/SignUp.tsx` (two in-page steps, `details` then `code`, not two routes), reusing `useSession()`'s new `startSignup`/`verifySignup` methods (`session.tsx`) rather than a separate session concept — a completed signup *is* a normal business session from that point on, unlike platform admin's genuinely separate identity space. `Login.tsx`'s "New here?" line now links to `/signup` instead of the old "your owner sets up your account first" copy, which was true before this existed and is not anymore.
- **`DashboardTour`** (`src/components/DashboardTour.tsx`, state/logic split into `src/lib/dashboardTour.ts` purely to keep the component file `react-refresh`-clean) shows a four-step spotlight walkthrough the first time `Dashboard` renders (tracked in `localStorage`, key `jb_dashboard_tour_seen` — a per-device UX nicety, not synced anywhere, intentionally not worth a backend column for this). Targets the same four anchor IDs `AppBottomNav`'s own links already jump to (`#quick-sell`, `#stock`, `#bills`, `#more`) rather than a generic tour library, since the tour only ever needs these four fixed, stable targets. Verified live end-to-end with Playwright: signup → OTP (read back out of the dev console-provider's log line, since there's no real SMTP configured in this environment) → onboarding → dashboard → tour appears, steps through, dismisses, and stays dismissed after a reload.

## OAuth

`internal/oauth` implements "Sign in with Google" as a second way into the *same* account system `internal/signup`/`internal/identity` already run — unlike platform admin, there is no separate identity space here. `docs/ARCHITECTURE.md` never mentions OAuth at all, so like platform admin and signup this was designed and confirmed in-session before being built (three explicit decisions: auto-link a Google sign-in to an existing password account by email, since Google's own verification of that email is at least as strong a proof as anything password signup gives; render the button on both `Login` and `SignUp`; and build it now rather than defer it).

- **Google Identity Services (GIS) ID-token flow, not a server-side redirect.** The frontend renders Google's own button, gets back a signed JWT, and POSTs it once to `POST /api/v1/auth/google` (public, unauthenticated, request body `{"id_token": "..."}`). The backend never talks to Google's token endpoint and never holds a client secret — it only verifies a token's signature. This was chosen over the classic Authorization Code redirect specifically because we don't need continued access to any Google API (just identity), so Authorization Code's extra machinery (refresh tokens, a `/callback` route, redirect-state handling inside a PWA/service-worker context) buys nothing here.
- **The verifier is hand-rolled, not a pulled-in JWT/OIDC library** (`internal/oauth/google_verifier.go`): RS256 signature check against Google's published JWKS (`https://www.googleapis.com/oauth2/v3/certs`, cached in memory for `jwksCacheTTL` = 1 hour, refreshed on an unrecognized `kid`), plus `iss`/`aud`/`exp` checks — all using only stdlib `crypto/rsa`. This mirrors `internal/auth.VerifyLease`'s own reasoning (see the Phase 2 section): the *format* is externally fixed here (unlike the offline lease, we don't get to design it away), but the *verification surface* is kept just as narrow — RS256 only, hardcoded, never negotiated from the token's own header, which is what closes off the classic JWT "algorithm confusion" foot-gun (e.g. accepting `alg: HS256` and treating the RSA public key as an HMAC secret). `TestGoogleVerifierRejectsNonRS256Algorithm` exercises exactly that rejection.
- **Response shape matches `POST /auth/login`/`POST /auth/signup/verify` exactly** — the frontend applies it through the same `applyMe` path (`useSession().continueWithGoogle`). A brand-new Google account has no memberships yet, so the existing "no memberships → `/onboarding`" redirect logic needs no special case for it.
- **Schema** (migration `000017`): `password_hash` on `users` is now nullable (a Google-only account has no password at all; `auth.VerifyPassword` already fails safely — `ErrInvalidHashFormat` — against an empty/NULL hash, so `Authenticate` needed no special case). `user_identities` (`provider`, `provider_user_id`, `user_id`, unique on `(provider, provider_user_id)`) is its own table rather than columns on `users`, no RLS (not tenant-owned, same reasoning as `users` itself) — this is what lets a user have both a password and a linked Google identity, and lets a second provider later need no new migration.
- **Three account-resolution cases**, all in `Service.resolveUser`: (1) `(google, sub)` already linked → log in as that user; (2) no link, but the email already has a password-based `users` row → auto-link and log in — safe specifically because Google, not the caller, verified that email; (3) no link, no existing user → create a new passwordless user (`identity.CreateUserWithoutPassword`) and link it, `is_new_account`-equivalent to a fresh signup. The link-write in cases 2 and 3 is deliberately **not** wrapped in the same transaction as the user lookup/creation before it (each `internal/identity` call is its own transaction, same as `internal/signup.Service.Verify`'s own best-effort cleanup) — if it fails, the account already exists and the sign-in still succeeds; the next sign-in attempt finds no link yet, re-enters the same branch, and retries it. Self-healing, not atomic, and documented as such at the call site.
- **Rate limiting is a single per-IP limiter** (`googleSignInIPLimiter`, 30/minute), much lighter than signup's three-layer defense — cryptographic ID-token verification isn't guessable the way a 6-digit OTP is, so this only needs to bound wasted verification work from garbage tokens, not defend against brute-forcing.
- **No dev fallback, unlike SMTP.** `internal/app.googleOAuthService` returns `nil` when `JBM_GOOGLE_OAUTH_CLIENT_ID` is unset, and `httpapi.NewHandler` only registers `POST /auth/google` when `Dependencies.OAuth != nil` — the feature is simply absent, not faked, and there's no production requirement for it either (it's an optional extra sign-in method, not core to the pilot). Frontend mirrors this with its own independent `VITE_GOOGLE_OAUTH_CLIENT_ID`: `GoogleSignInButton` renders nothing when it's unset.
- **Frontend**: `src/components/GoogleSignInButton.tsx` lazy-loads Google's `accounts.google.com/gsi/client` script once (cached on the module, not per-mount) and renders Google's own button via `renderButton`; on success it calls `useSession().continueWithGoogle(idToken)`. Rendered identically on `Login.tsx` and `SignUp.tsx` below a plain "or" divider — there's no meaningful product difference between "sign in" and "sign up" with Google, since neither collects a password up front; the backend's three-case resolution above is what actually decides which one it turns out to be.
- **Not yet verified live end-to-end**, unlike every other feature in this file: doing so needs a real Google Cloud OAuth Client ID and an actual Google account, which this dev environment doesn't have configured. Backend logic is covered by `internal/oauth`'s tests (a fake `IDTokenVerifier` for `Service`, a real self-signed-JWT-against-a-local-JWKS-server for `GoogleVerifier`) instead. Whoever configures a real `JBM_GOOGLE_OAUTH_CLIENT_ID`/`VITE_GOOGLE_OAUTH_CLIENT_ID` pair should manually run all three resolution cases at least once before trusting this in production.
- **Deployment note for later**: the API's own `Content-Security-Policy` (`internal/httpapi/middleware.go`, `default-src 'none'`) doesn't apply to the frontend's static assets, since nothing in this repo serves those yet (per `docs/ARCHITECTURE.md` §16.3, that's a still-unbuilt deployment piece). Whatever eventually serves `index.html` will need a CSP permissive enough for GIS (`script-src`/`connect-src`/`frame-src` including `https://accounts.google.com`) — don't copy the API's `default-src 'none'` verbatim onto it.

## Invitations and WhatsApp messaging

`internal/whatsapp`, `internal/verification`, and `internal/invitations` implement dual phone/email identity and staff invitations delivered over WhatsApp (via Zavu, a third-party messaging relay) or email. Like platform admin, signup, and OAuth before it, `docs/ARCHITECTURE.md`/`docs/IMPLEMENTATION_PLAN.md` never designed this — it was designed and confirmed in-session once a real Zavu business account existed to build against. Full design record, confirmed decisions, and the NDPA compliance assessment live in `docs/PHASE_INVITATIONS_WHATSAPP.md` — read it before extending any of this.

- **Dual identity, not phone-as-an-extra-field.** `users.email` is now nullable (`CHECK (email IS NOT NULL OR phone IS NOT NULL)`, migration `000021`) — the same nullable-column precedent OAuth set for `password_hash`. `users.phone` existed unused since migration `000002`; this phase is what finally uses it. Either identifier can sign up, log in (`identity.Service.Authenticate` detects email vs. phone by format), or be the target of an invitation. **Known limitation, accepted not fixed**: phone is a single column, not a set — verifying a new phone through the invitation-link flow overwrites whatever phone the account already had rather than tracking several.
- **`internal/whatsapp` mirrors `internal/email`'s exact shape** — `Provider` interface (`Send(ctx, Message) (messageID string, err error)`), `ZavuProvider`, `ConsoleProvider` (dev fallback, logs instead of sending), `WithRetry` decorator. `ZavuProvider` talks to Zavu's REST API directly over `net/http` (`POST https://api.zavu.dev/v1/messages`, bearer key, `Zavu-Sender` header) — the `github.com/zavudev/zavu-go` module the initial design sketch assumed does not actually exist (`go list -m` returns "Repository not found"); the real contract came from Zavu's published docs instead. `internal/whatsapp/webhook.go`'s `VerifySignature` checks `X-Zavu-Signature: t=<ts>,v2=<hmac>` (HMAC-SHA256 over `"{ts}.{body}"`, constant-time compare, rejects if the timestamp is more than 5 minutes old or 60 seconds in the future) for `POST /api/v1/webhooks/zavu`'s delivery-status callbacks.
- **Config is enforced like SMTP, not like OAuth**: `config.Zavu.Configured()` (API key + sender ID) gates `config.Load()`'s production-required check, same pattern as `config.SMTP.Configured()`. Outside production, missing credentials fall back to `ConsoleProvider` automatically.
- **`JBM_PUBLIC_BASE_URL` must be the frontend's own origin, not this API's address** — a real trap, hit live: `internal/invitations.Service.Create` builds every invitation link as `"{JBM_PUBLIC_BASE_URL}/invite/{token}"`, and `/invite/:token` is a React Router route the Vite frontend serves (`web/src/app/App.tsx`), not an API endpoint. Pointing it at the Go API's own address (an easy mistake — `.env` briefly had it set to `JBM_HTTP_ADDR`'s port) produces a link that 404s the moment anyone opens it, since the backend has no such route registered. Locally this is the Vite dev server's fixed port, `http://localhost:5173` (`web/vite.config.ts`), never `JBM_HTTP_ADDR`'s port; in production it's wherever the built frontend is actually served from.
- **`internal/verification`'s `identity_verifications` table is the "verify before link" mechanism** — proving control of a *new* identifier before attaching it to an *already-existing* account, distinct from both `signup_verifications` (brand-new account) and `invitations` (brand-new membership). Shared by two purposes (`PurposeAddIdentifier` from account settings, `PurposeInvitationLink` from the invitation flow below) — `internal/verification` itself doesn't know or care which one triggered it. 3-attempt lockout (tighter than signup's 5, since this guards an account merge), 10-minute OTP TTL.
- **`internal/invitations`' asymmetric channel defaults are deliberate, not a blanket "WhatsApp everywhere" policy**: self-service signup defaults to email, WhatsApp as an explicit alternative (higher volume, cost-sensitive — email is free, WhatsApp business-initiated messaging isn't); staff invitations default to WhatsApp when a phone is given, email otherwise (lower volume, bounded by headcount, and bar staff skew even less email-native than owners). Neither is a hard restriction, just which option is presented first.
- **Two acceptance paths, both in `invitations.Service`**: `AcceptAsNewUser` (flow D, "I'm new here") creates the account and grants membership in one call with **no OTP challenge** — receiving the invitation already proved channel ownership. `AcceptAsExistingUser` (flow E's last step, "I already have an account") only finalizes a membership grant; the caller (the HTTP handler) must already have verified the invitation's identifier belongs to that user, either because it already matched an identifier on their account or because `internal/verification` just confirmed a fresh OTP for it — `AcceptAsExistingUser` itself does not re-verify, matching the codebase's "resolve first, mutate once trusted" discipline used elsewhere (e.g. the bill-lifecycle code in Tabs and credit).
- **`identity.ErrAlreadyMember` is treated as a fulfilled invitation, not a failure**, inside `AcceptAsExistingUser` — found and fixed via live testing (a re-invited existing staff member used to get a raw 500). The practical goal an invitation exists for — a verified identifier plus real business access — already holds in that case, so the invitation is marked accepted instead of rejected. See `TestAcceptAsExistingUserTreatsAlreadyMemberAsFulfilled`.
- **The `invitations` table is deliberately not RLS-scoped**, unlike almost every other tenant-owned table in this codebase — same reasoning as `signup_verifications`/`sessions`. The public token-lookup/accept endpoints (`GET /invitations/{token}`, `POST /invitations/{token}/accept`) are hit by an anonymous invitee with no tenant context; an RLS policy keyed on `app.business_id` would return zero rows for them. The row's own unguessable hashed token is the access control. Authenticated, owner-facing queries (`List`, `Revoke`) filter by `business_id` explicitly in SQL instead.
- **Package-boundary discipline**: `internal/invitations` does not import `internal/verification`. The orchestration between "verify this identifier" and "then grant this membership" lives in the HTTP handler layer (`confirmIdentityVerification` in `internal/httpapi/verification_handlers.go`, via an optional `invitation_token` pass-through field on the confirm request) rather than either feature package reaching into the other.
- **Endpoints**: reuses the existing `members:read`/`members:manage` capabilities, no new permission design needed. `POST/GET /invitations`, `POST /invitations/{id}/revoke` are business-scoped (owner-only for the mutating two). `GET /invitations/{token}`, `POST /invitations/{token}/accept`, and `POST /webhooks/zavu` are fully public. `POST /invitations/{token}/link`, `POST /identity-verifications/{id}/confirm`, and `POST /me/identifiers` are authenticated but not business-scoped (an invitee linking an invitation, or a user adding an identifier, doesn't need an active `X-Business-ID` to do either).
- **Phone numbers are validated as E.164 at every boundary that hands one to `internal/whatsapp`** (`createInvitation`, `signupStart`'s WhatsApp channel, `startAddIdentifier`) — `validator.IsE164Phone` (`internal/validator/validator.go`, a plain regex), added after a live invitation with a locally-formatted phone (e.g. `0803...`) sailed through every existing check and only failed once it hit Zavu's API, surfacing as an unhandled `500` instead of a normal `422 VALIDATION_FAILED`.
- **Frontend**: `src/lib/session.tsx`'s `login`/`startSignup`/`verifySignup` are generalized to `(identifier, password)` / `(channel, identifier, name, password)` / `(channel, identifier, code)`; `login` returns the fresh CSRF token directly from its response rather than making a caller wait a render for context to update — `InviteAccept.tsx`'s "sign in, then immediately link" step depends on this. A new `acceptInvitation(token, name, password)` context method covers flow D, reusing the same `applyMe` session-establishing path as login/signup verify. `src/api/invitations.ts` is the typed client for the rest (create/list/revoke/getByToken/link/confirm). `src/pages/SignUp.tsx` gained an email/WhatsApp channel toggle (email default); `src/pages/Login.tsx`'s single email field became a generic identifier field. `src/pages/InviteAccept.tsx` (public `/invite/:token`) implements flows D and E end-to-end, including the verify-then-link OTP step. `src/pages/Team.tsx` (`/dashboard/team`, linked from Dashboard's "More" section) is the owner-facing invite/list/revoke screen — Staff can view the list (`members:read`) but the invite form and revoke buttons only render for Owners, mirroring `Tabs.tsx`'s existing `isOwner` client-side gating pattern. `src/components/PhoneInput.tsx` (a country-code-plus-local-number picker, flags computed from ISO2 via `src/lib/countryCodes.ts`, always composing a real E.164 string) replaced a bare `<input type="tel">` on both `SignUp.tsx`'s WhatsApp channel and `Team.tsx`'s invite form after a malformed phone reached Zavu and came back as a raw 500 (see the `validator.IsE164Phone` note above). `src/components/ChannelIcon.tsx` (`WhatsAppIcon`/`EmailIcon`, `currentColor` throughout so each inherits its button's existing text color) sits before the label on every WhatsApp/Email channel toggle. `Team.tsx`'s email-channel view also carries a short reminder for the *inviter* — invite emails can land in spam, so ask your invitee to check there — since that's exactly what happened once in this pilot's own testing.
- **No frontend UI yet for flow C** ("add a phone/email to my account" from account settings) — the backend endpoints (`POST /me/identifiers`, `POST /identity-verifications/{id}/confirm`) exist and work, `internal/verification` doesn't care where a challenge came from, but no settings screen calls them. Deliberately deferred: flows D and E were the priority since they're what actually gets a second person into a business.
- **Verified live end-to-end** against a running backend, using the frontend's own exact request/response shapes over curl (not just unit tests): dual-identity signup and login by both email and phone, invitation create → accept-as-new-user, invitation create → link-as-existing-user through the full verify-then-link challenge in both directions, duplicate-invitation rejection, and revoke. Test data cleaned up afterward the same RLS-aware way `platformadmin.service_test.go`'s `cleanupBusiness` does (`SET LOCAL ROLE jbm_app` + `app.business_id` inside a transaction) — a plain `DELETE` under this environment's non-superuser `JBM_DATABASE_URL` role silently affects zero rows on RLS-scoped tables otherwise, per this file's own Commands-section warning above.
- **This is also the Phase 4 trigger** (recorded in project memory as `phase4-sync-foundation-deferred`): Phase 4 (multi-device sync) was deferred specifically "until invitations bring a second device into a real business." Building invitations doesn't itself build Phase 4 — but once a real invitation is accepted on a second device, that's the point to revisit it, not something solved preemptively here.

## Frontend architecture

`web/` is a single Vite + React + TypeScript + Tailwind v4 PWA that carries **both** the public marketing/onboarding site and the authenticated app shell — there is no separate marketing project. It used to be split across two stacks (this Vite app plus a Next.js prototype in `marketing/`, built from a v0 export template); that Next.js app has been retired and its design system (brand tokens, fonts, and reusable components) ported in here. The v0 template it was originally adapted from was kept read-only at `agentic-build-and-orchestrate-ai-agents-while-you-sleep/` at the repo root purely as a design reference; it has since been deleted (its design system was already fully ported into `web/` by this point, so nothing was lost) — don't expect to find it, and never resurrect a second frontend stack from a copy of it.

Routes (`src/app/App.tsx`, `react-router-dom`): `/` (landing page), `/login`, `/signup`, `/invite/:token` (public invitation landing page, see the Invitations and WhatsApp messaging section), `/onboarding` (4-step wizard — step 1 is a real `POST /businesses`, steps 2-3 are still a UI preview of product/price setup pending Phase 3), `/install` (PWA install guide that performs real device enrollment), `/dashboard`, `/dashboard/sell`, `/dashboard/stock`, `/dashboard/tabs`, and `/dashboard/team` (the app shell — auth, business identity and offline-lease status are real; some dashboard figures are still mock data pending later phases, see the Tabs and credit section). The public pages (`/`, `/login`, `/signup`, `/invite/:token`) need no auth; `/onboarding`, `/install`, `/dashboard*` are wrapped in `RequireAuth`, and the dashboard routes additionally pass `requireBusiness` (see below). The public pages (`/`, `/onboarding`, `/install`) have no offline requirement; only the `/dashboard*` app screens do, per `docs/ARCHITECTURE.md`.

Phase 2 frontend wiring (login, business creation, device enrollment) is real and hits the Go backend:

- `src/lib/session.tsx` — `SessionProvider`/`useSession`: calls `GET /me` on mount, caches the resulting identity in IndexedDB (`src/lib/db.ts`, via Dexie) and falls back to that cache when `/me` fails for a non-401 reason (offline), so a reload while offline doesn't bounce an already-signed-in user to `/login`. A 401 is the only thing that clears the cache and flips to `anonymous`.
- `src/lib/device.ts` — generates and persists a per-device Ed25519 keypair (WebCrypto) in IndexedDB on first use; `src/lib/lease.ts` decodes and verifies a `v1.<payload>.<signature>` offline-authorization lease **entirely client-side** against `VITE_OFFLINE_SIGNING_PUBLIC_KEY`, mirroring `internal/auth.LeasePayload` byte-for-byte. `src/lib/base64.ts` has separate URL-safe/unpadded (`base64UrlEncode/Decode`, matches Go's `RawURLEncoding`) and standard/padded (`base64Encode/Decode`, matches `StdEncoding`) codecs — using the wrong one silently corrupts signature verification.
- `src/components/RequireAuth.tsx` — gates on session `status`; pass `requireBusiness` for any route that assumes a business already exists (currently `/dashboard`, `/dashboard/sell`) so a signed-in user with zero memberships is bounced to `/onboarding` **even if they reach the URL directly** (bookmark, back button, or a stale post-login `from` redirect) rather than only relying on `Login.tsx`'s own post-login routing decision — the two real bugs below are exactly why this exists as a second, independent layer rather than one.

Two non-obvious bugs were found and fixed while wiring this up, verified live against a real `go run ./cmd/api` — both are permanent traps for this exact pattern (auth guard + redirect-back), not one-off mistakes:

1. **Vite's dev `/api` proxy silently breaks the backend's CSRF check.** `internal/httpapi` requires the `Origin` header's host to equal the request's `Host` header (see `middleware_auth.go`'s `requireCSRF`) — correct and sufficient in production, where the frontend and API share one origin. But Vite's dev proxy (`server.proxy`) rewrites the outgoing `Host` header to the proxy target (`localhost:8080`) while the browser's real `Origin` stays `localhost:5173`, so every authenticated `POST`/`PUT`/`PATCH`/`DELETE` in dev gets rejected with `PERMISSION_DENIED` / "not a trusted origin" — confirmed by proxying to a throwaway echo server and inspecting the headers it actually received. Fixed in `vite.config.ts` by re-pinning the proxied request's `Host` header back to the original inbound one via the proxy's `configure`/`proxyReq` hook. If a future upgrade of Vite/its proxy layer changes this default again, this is the symptom to look for.
2. **A same-render state race in `Onboarding.tsx` could bounce a user away from the business they just created.** Creating a business calls `addMembership` (updates `SessionProvider`'s state) and then `setStep(2)` (local state) — two separate `setState` calls separated by an `await`, so React can commit a render in between where `memberships` is already non-empty but `step` is still `1`. The step-1 guard (`memberships.length > 0 && step === 1` → redirect to `/dashboard`, meant only for a returning user who already has a business) fired on that in-between render and skipped straight past product/price setup. Fixed by capturing "did this user already have a business" **once, at mount** (`useState(() => memberships.length > 0)`), not by reading the live `memberships` value in the guard.

Offline-first is the real, load-bearing requirement for the app shell: IndexedDB (via Dexie, once introduced) is meant to be the operational source of truth for business data there, not an in-memory store or query cache. This is also *why* the app was kept on Vite rather than moved to Next.js — Next.js's default rendering mode does per-navigation server round-trips that a service worker cannot cleanly serve from cache, which conflicts with a hard requirement that the app survive an offline reload with pending sales still visible; `output: 'export'` would avoid that but at that point buys nothing Vite doesn't already give more simply.

- `src/styles/global.css` — Tailwind v4 entry point. Brand tokens (`--color-jb-cream`, `--color-jb-ink`, `--color-jb-green`, `--color-jb-green-dark`, `--color-jb-gold`) are defined with **literal values directly in a plain `@theme` block**, not `@theme inline` aliasing a separate `:root` block — that indirection is only needed for tokens that must re-resolve at runtime (e.g. light/dark toggling), which this project doesn't use, and it silently broke Tailwind's utility generation for the bare (non-opacity-suffixed) form of every one of these tokens. Custom base-layer resets (`html`, `body`, `a`, focus rings) are wrapped in `@layer base` — **never leave custom global CSS unlayered** here: an unlayered rule beats every Tailwind utility regardless of specificity, which previously made every `text-*` utility on every `<a>`/`Link` silently no-op in favor of an inherited color. Also: a literal `{ }` pair inside a CSS *comment* was enough to break the Tailwind/Lightning CSS parser with a "Missing opening (" error — keep comments in this file free of brace characters.
- Fonts are self-hosted via `@fontsource` (not Google Fonts CDN) so the app keeps working fully offline: Geist Sans/Mono ship Latin-only already; IBM Plex Sans does not, so it's imported via its `latin-*.css` files specifically (its plain weight files bundle six scripts — cyrillic, greek, vietnamese, etc. — that would otherwise bloat the PWA's precached assets for a Latin-script audience for no benefit).
- `src/components/PixelIcon.tsx`, `RevealText.tsx`, `Logo.tsx`, `PhoneFrame.tsx`, `UiPreviews.tsx`, `MobileNav.tsx`, `AppBottomNav.tsx`, `IntroAnimation.tsx` — the ported design-system components. `PixelIcon` draws to a `<canvas>`; jsdom has no canvas support, so `src/test/setup.ts` logs (harmless) "not implemented" warnings under `vitest` — that's expected, not a bug to fix.
- `src/api/client.ts` — `apiRequest<T>` wraps `fetch`, enforces `credentials: 'same-origin'`, and unwraps the `{data}`/`{error}` envelope into a typed result or a thrown `ApiError`. Route new API calls through this rather than calling `fetch` directly. It also catches `fetch` itself throwing (a dropped connection, DNS failure, etc.) and re-throws a distinct `OfflineError` with a fixed, plain-language message ("You're offline. This needs an internet connection to work.") instead of letting a cryptic browser `TypeError` reach a page's catch block — deliberately **not** a proactive `navigator.onLine` check before the request, since `useConnectivity.ts`'s own doc comment already says that flag is a hint, not proof, and a real e2e test (`e2e/offline.spec.ts`, aborting every `/api/v1/**` request) caught exactly this when an earlier draft tried the proactive check and broke an unrelated connectivity test that intentionally sets `navigator.onLine = false` while still expecting a mocked `fetch` to succeed. `src/lib/errors.ts`'s `describeActionError(err, fallback)` is the one place every page's catch block should turn a failed mutation into user-facing text — `OfflineError`/`ApiError` messages pass through, anything else falls back to the caller's own generic text — applied across every page with a real mutation (`Tabs.tsx`, `Team.tsx`, `Stock.tsx`, `Sell.tsx`, `Install.tsx`, `Onboarding.tsx`, `InviteAccept.tsx`, `GoogleSignInButton.tsx`, `PlatformDashboard.tsx`). The two login forms (`Login.tsx`, `platform/PlatformLogin.tsx`) and `InviteAccept.tsx`'s existing-account login step are the deliberate exception: they check `OfflineError` as an explicit first branch rather than routing through `describeActionError`, since their own fallback text ("Incorrect email/phone or password") is intentionally opaque about *why* a login failed (per `docs/API_CONTRACT.md` §8) and must not be silently replaced by a connectivity message that would be flat wrong while genuinely offline.
- `src/hooks/useConnectivity.ts` — thin `navigator.onLine` wrapper via `useSyncExternalStore`. This is a hint only, per the architecture doc; do not treat it as proof of real connectivity for sync decisions.
- `src/hooks/useServiceHealth.ts` — polls `/api/v1/health/ready` to distinguish `checking`/`available`/`unavailable`/`offline`; surfaced on the dashboard via `StatusBadge`.
- Vite dev server proxies `/api` to `VITE_API_PROXY_TARGET` (with the `Host`-header fix above), defaulting to `http://localhost:8080` if unset — run the Go backend alongside `npm run dev` for real API integration. `web/.env` needs `VITE_OFFLINE_SIGNING_PUBLIC_KEY` set to the same value as the backend's `JBM_OFFLINE_SIGNING_PUBLIC_KEY`, and **`VITE_API_PROXY_TARGET` must match the backend's actual `JBM_HTTP_ADDR` port** (in the *root* `.env`, a separate file `vite.config.ts` has no automatic way to see). These drifting apart is a real outage that already happened once: every `/api/*` request silently 502s, which the platform login page reports as "could not reach the platform admin API" — easy to misread as wrong credentials rather than a proxy misconfiguration. If a login "fails" with credentials you're sure are right, check this before the account.
- PWA config (`vite-plugin-pwa` in `vite.config.ts`) explicitly denylists `/api/` from the navigation fallback and starts with no runtime caching — do not cache authenticated API responses in the service worker; persist controlled data in IndexedDB instead, per the architecture doc. App icons are generated from `logo.svg`/`logo.png` at the repo root (`public/icon.svg`, `icon-192.png`, `icon-512.png`) — regenerate the PNGs with `rsvg-convert` (or equivalent) rather than hand-editing them if the mark changes.
- ESLint uses flat config with `typescript-eslint` recommendedTypeChecked plus `react-hooks`/`react-refresh` — `npm run lint` requires zero warnings (`--max-warnings 0`). `tsconfig.app.json` has `noUncheckedIndexedAccess: true`; array-destructured callback params (e.g. an `IntersectionObserver` entry) need an `entry?.` guard, not a bare access.

## Working agreement (from `docs/IMPLEMENTATION_PLAN.md`)

Backend and frontend are treated as separately owned scopes with a phase-gated workflow: each phase has a frozen contract, backend implements it, then frontend implements against the frozen contract. When implementing a phase, stay inside that phase's listed scope — the plan explicitly calls out non-goals per phase (e.g., Phase 1 must not create auth/tenancy/domain packages or `sqlc` output). Check `docs/IMPLEMENTATION_PLAN.md` for the current phase's task list and acceptance criteria before adding new backend packages.
