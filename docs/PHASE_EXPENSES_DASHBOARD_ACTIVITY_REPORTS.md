# Phase 8 — expenses, dashboard, activity, and reports

**Status:** Built and live-verified (backend end-to-end via curl; frontend via the full `tsc`/`eslint`/`prettier`/`vitest`/`build` check suite — see §8 for exactly what was verified). Matches `docs/IMPLEMENTATION_PLAN.md`'s actual Phase 8 ("Expenses, dashboard, activity, and reports"), narrowed and made concrete the same way Phase 7 was before implementation began. See §7 for the confirmed decisions.
**Depends on:** `internal/sales` (sales/bills/payments), `internal/inventory` (receiving, counts, adjustments, reviews — all built), `internal/identity` (roles/capabilities, business timezone).
**Builds on:** everything shipped so far — this phase is mostly *reading* what earlier phases already post, plus one genuinely new domain (expenses).

## 2. Schema (new migration `000023`)

One new domain, following the exact `sale_reviews`/Phase 7 precedent (narrow, purpose-built, `business_id` + composite FKs + `FORCE ROW LEVEL SECURITY` + `NULLIF(current_setting(...), '')::uuid` policy):

- **`expense_categories`** — `business_id`, `name` (unique per business), `active` (never hard-deleted, same convention as `categories`/`products`).
- **`expenses`** — `business_id`, `location_id`, `category_id`, `description`, `amount_kobo` (positive), `payment_method` (reuse the existing `cash`/`transfer`/`card` enum `payments.method` already uses — no need to invent a second one), `recorded_by`, `idempotency_key` (client-generated, business-scoped unique — same reasoning as `sales.idempotency_key`: this is offline-safe, see §4), `occurred_at`, `reversal_of_expense_id` (nullable, self-referencing FK — mirrors `sales.reversal_of_sale_id`), `created_at`.

No new review type and no changes to `inventory_events`/`inventory_reviews` — expenses don't touch inventory at all (an expense is money out, not stock movement; if a business logs "bought cleaning supplies" as an expense, that's correct — it never becomes a stock receipt unless it's actually inventory, which goes through `/dashboard/stock` instead).

## 3. Backend behavior

- **`internal/expenses`** (new package, self-contained per this codebase's package-boundary rule — does not import `internal/sales`/`internal/inventory`): `RecordExpense` (idempotent, same first-check-the-key-inside-the-transaction pattern as `sales.CreateSale`), `ReverseExpense` (creates a new, equal-and-opposite record — never edits or deletes, same as `sales.ReverseSale`; §7 Q2 asks who may call it), `ListExpenses`, `ListCategories`, `CreateCategory`.
- **Recorded expenses are immutable**, same rule as every other posted financial record in this codebase. A "corrected" expense is a reversal plus a new expense, never an `UPDATE`.
- **Activity feed: a query-time `UNION ALL` view, not a new `activity_events` writer table** (confirmed, §7 Q1). `internal/store/queries/activity.sql`'s `ListActivity` is one `UNION ALL` across `sales` (reversals included — real activity too), `expenses`, `inventory_adjustment_requests` (`status='approved'`), and `stock_receipts`, each projected into one common shape (`id`, `type`, `actor_id`, `occurred_at`, `summary`, `amount_kobo` nullable), ordered by `occurred_at desc`, filtered by `business_id` plus optional `actor_id`/`type`/`date range`. Same reasoning that already kept this codebase off the generic `review_cases` table and the generic Phase 4 sync protocol — solve the concrete, present need with the narrowest real mechanism.
- **`GET /api/v1/dashboard`** (new, matching `docs/ARCHITECTURE.md` §12's own sketch, confirmed §7 Q4) replaces `Dashboard.tsx`'s current three separate calls with one round trip, composed the way `GET /products` already composes `catalogue` + `inventory` at the HTTP layer — the handler calls each domain package's own method (`sales.SumSalesTotalSince`, `sales.ListSales`, `inventory.ListOpenReviews`, `expenses.SumExpensesSince`, the new activity union), run concurrently via a plain `sync.WaitGroup` (no new dependency — matches this codebase's stdlib-first preference), and composes one JSON response: today's sales total/count, items sold today, today's expenses total, outstanding bills total, an alerts count (open `inventory_reviews` + open `sale_reviews` + pending `inventory_adjustment_requests` — a real number, replacing the hardcoded stock-alerts mock), and the last few activity-feed entries. **Capability-aware, not capability-gated as a whole**: the handler checks `business.Has(capability)` per section (`reports:read` for sales-summary/items-sold/expenses, `activity:read` for recent-activity, `bills:read` for outstanding) and omits a section the caller's role can't see rather than 403ing the entire response — this fixes a real, currently-live gap: Staff has neither `reports:read` nor `activity:read`, so today's three-separate-call `Dashboard.tsx` silently 403s two of three for a Staff viewer and shows blank cards via the swallowed `.catch()`. `GET /dashboard` needs no capability check of its own beyond `requireAuth`/`requireBusinessContext` — every field it might return is already gated per-section.
- **Reports** (`GET /api/v1/reports/{sales,products,staff-sales,expenses,stock,outstanding}`, `reports:read`, all six built this pass — confirmed §7 Q3 — date-range-bounded in the business's own timezone per `docs/ARCHITECTURE.md` §14):
  - `sales` — totals/count by day within a range (the same day-bucketed rows the Reports page's heatmap renders — see §5).
  - `products` — quantity sold per variant within a range (a straightforward `SUM(sale_items.quantity)` group-by, excluding reversal rows' negative quantities from a "units sold" figure the same way `today_sale_count` already excludes reversals from a count).
  - `staff-sales` — totals grouped by `seller_id`, names resolved the same way `resolveSellerNames` already does everywhere else.
  - `expenses` — totals grouped by `category_id` within a range.
  - `stock` — reuses Phase 7's own data directly: stock count lines with nonzero variance, plus resolved/open `inventory_reviews`, within a range. No new schema needed.
  - `outstanding` — **no new endpoint.** `GET /bills?status=outstanding` already returns exactly this; the Reports page calls the existing endpoint.
- **Expense listing/reporting capability**: reuses `activity:read` (listing) and `reports:read` (reports/dashboard), same as sales — no new capability constants needed.
- **Whether Staff can see their own expense history remains the same open pilot question already on record for sales** (`docs/CLAUDE.md`'s Walk-in selling section) — not resolved here, carried forward, Owner-only by default like `listSales`.
- **Pagination**: keep the existing `limit`-only convention (`GET /sales?limit=`, `GET /inventory-reviews`) for the new activity/report endpoints too, rather than introducing cursor pagination — a single pilot bar's daily transaction volume doesn't yet justify it, and every existing list endpoint in this codebase uses the same simple pattern.

## 4. Offline support

`expenses:record` **is already in `offlineSafeCapabilities`** (`internal/tenancy/capabilities.go` — anticipated back in Phase 2, same as `inventory:count`/`inventory:adjustment_request` were before Phase 7). Recording an expense gets real offline queueing, mirroring `Sell.tsx`'s IndexedDB-first pattern exactly (a fourth Dexie table, `pendingExpenses`, a fourth `flushPending*` in a small `expensesSync.ts`, or folded into the existing `inventorySync.ts`-style module). `expenses:reverse` is Owner-only and **not** offline-safe, same tier as `sales:reverse`/`inventory:adjustment_approve` — reversal always requires online server authorization.

Dashboard, activity, and reports are all read-only owner-facing views with no offline-write requirement — they follow the existing "best-effort, renders empty/stale if the fetch fails" pattern `Dashboard.tsx` already uses, not a new caching mechanism.

## 5. Frontend

- **A new expense entry form** (`web/src/pages/Expenses.tsx`): category picker (with an inline "add category" affordance, mirroring `Stock.tsx`'s inline-create pattern), description, amount, payment method, offline-first submission per §4.
- **`Dashboard.tsx` rewired** to the new `GET /dashboard` endpoint: real "items sold" and "today's expenses" figures, a real alerts count replacing the "3 items low" mock, and a unified recent-activity feed (sales + expenses + adjustments + receipts, not sales-only) — and, as a side effect, the Staff-viewer blank-cards gap above is fixed for free.
- **A new Activity page** (`/dashboard/activity`): a GitHub-style daily-activity-count heatmap up top (a plain CSS grid of colored cells, no charting library — matches this codebase's minimal-dependency ethos, e.g. the hand-rolled JWT verifier and self-hosted fonts) sourced from the same day-bucketed activity counts as the list below it, then the full feed with actor/type/date filters, reachable from Dashboard's "More" menu alongside Team/Reviews. Clicking a heatmap day filters the feed to that day.
- **A new Reports page** (`/dashboard/reports`), confirmed shape per §7 Q5:
  - **Sales** — a daily-revenue heatmap (same cell-grid component as Activity's, different intensity metric) plus the day-bucketed totals table underneath.
  - **Expenses** — a category breakdown (bar list, ranked by total) as the primary view; no heatmap here, since "when" is less actionable than "what" for expenses.
  - **Products, staff sales, stock discrepancies** — ranked tables/simple bar lists, not heatmaps (categorical/ranked data, not daily-continuous — a heatmap would be sparse and harder to read than a sorted list for these).
  - **Outstanding** — renders the existing `GET /bills?status=outstanding` data, no new client call.
  - A "provisional/offline" indicator per the plan's own frontend task list, matching `docs/ARCHITECTURE.md` §10.7's honest-sync-state philosophy already used for the cached catalogue banner.
- **`HeatmapGrid` component** (new, `web/src/components/HeatmapGrid.tsx`): the one shared piece behind both heatmaps above — takes `{date, value}[]` and a color-intensity scale, renders a week-columns/day-rows CSS grid. Built once, reused by Activity and Sales-report rather than duplicated.

## 6. Explicitly out of scope

- **Low-stock threshold alerts / reorder points.** Phase 7 already named this out of scope; nothing about Phase 8 changes that. The dashboard's "alerts" figure counts *open reviews and pending adjustments*, not stock-level thresholds — a real number, but not the same thing a "3 items low" card implies today. Worth naming explicitly so the mock isn't replaced with something that looks like it solves low-stock alerting when it doesn't.
- **FIFO/COGS or any authoritative profit figure** — `docs/ARCHITECTURE.md` §14 explicitly says not to show authoritative gross profit while unresolved inventory quantities exist; this phase's reports stay revenue/expense/quantity, not margin.
- **PDF export of reports** — browser print/share only, if anything; no server-side PDF generation (that's Phase 9's receipts/sharing territory, not this one).
- **Multi-location reporting** — no report UI exposes `location_id`, same as every other screen in this codebase today.
- **A generic `activity_events` writer table or the frozen `review_cases` design** — see §3's activity-feed reasoning; this stays a read-time projection.
- **A charting library** (`recharts`/`visx`/`d3`/etc.) — the heatmap and every other Reports/Activity visualization are plain CSS grids/lists, no new frontend dependency.
- **Heatmaps on categorical/ranked data** (products, staff sales, stock discrepancies) — deliberately tables/bar lists instead, per §5.

## 7. Confirmed decisions (for the record)

1. Activity feed is a query-time `UNION ALL` view, not a new `activity_events` writer table.
2. Expense reversal is Owner-only (`expenses:reverse`), same tier as `sales:reverse`/`inventory:adjustment_approve`.
3. All six report views (sales, products, staff-sales, expenses, stock, outstanding) are built this pass.
4. `Dashboard.tsx` is rewired to one new, capability-aware `GET /dashboard` endpoint (§3) — chosen over leaving the three existing calls alone because it also fixes the live Staff-viewer blank-cards gap identified during this design pass.
5. GitHub-style heatmaps are used for Activity's daily-activity-count view and the Sales report's daily-revenue view — the two genuinely daily-continuous datasets. Everything else (expenses, products, staff sales, stock discrepancies) uses ranked tables/bar lists instead; no charting library is introduced, the heatmap is a hand-rolled CSS grid component shared by both uses.

## 8. Implementation notes

Built exactly to the design above, migration `000023_expenses`. Two things worth recording that weren't visible from the design alone:

- **sqlc's static analyzer cannot handle a `UNION ALL` inside a `WITH` clause feeding a `GROUP BY`/`date_trunc` aggregate** — `internal/store/queries/activity.sql`'s original single combined "count all activity by day" query reliably tripped a false-positive "column reference is ambiguous" error, and reusing one positional parameter (`$1`) across several UNION branches referencing different tables triggers the same false positive even with no aggregate involved (sqlc appears to merge every branch's range table when resolving a shared parameter, something real Postgres never does). Fixed two ways: (1) every UNION branch in `ListActivity` aliases its table and qualifies every column, including `business_id`, even though that's redundant under real Postgres; (2) the combined day-count query was split into four separate, single-table queries (`CountSalesByDay`, `CountExpensesByDay`, `CountApprovedAdjustmentsByDay`, `CountStockReceiptsByDay`), merged into one `day -> count` map in `internal/activity.Service.CountByDay` — simpler to read individually besides. Also: `AT TIME ZONE $N` needs an explicit `::text` cast on the parameter, or sqlc infers `pgtype.Interval` instead of a plain string (Postgres's `AT TIME ZONE` operator is overloaded between a zone-name and an interval-offset form, and sqlc's inference picks the wrong one without the cast).
- **`internal/sales` gained one new query** (`SumItemsSoldSince`, mirroring `SumSalesTotalSince`'s exact shape) to back the dashboard's "items sold" figure — not part of the original schema/domain sketch in §2/§3 but a natural extension of the existing sales package rather than a new one.
- **Backend live-verified end-to-end against an isolated instance** (curl, never the developer's own dev port): expense category creation/listing, idempotent expense recording, reversal creating a real equal-and-opposite record, double-reversal rejected with `409`; the unified activity feed correctly combining a sale, a stock receipt, and two expenses (one reversed) with the documented cash-impact sign convention, and its `type` filter; the day-count heatmap endpoint bucketing correctly; all five new report endpoints (`sales`, `products`, `staff-sales`, `expenses`, `stock`) returning correct figures, including a stock count's variance showing up in the stock-discrepancies report with no new schema; the capability-aware `GET /dashboard` returning the full response for an Owner and — the specific bug this design pass found and fixed — a correctly *partial* `200` response (just `outstanding_kobo`) for a Staff viewer, where the old three-separate-call frontend used to silently 403 two of three calls; and the full Staff/Owner permission split across every new endpoint (Staff: `201` recording an expense, `403` listing expenses/reversing/reading activity/reading reports). Test data cleaned up via the RLS-aware `SET LOCAL ROLE jbm_app` transaction pattern.
- **Frontend**: `web/src/lib/db.ts` gained `pendingExpenses` (Dexie version 5); `web/src/lib/expensesSync.ts` mirrors `inventorySync.ts`/`salesSync.ts` exactly. `web/src/api/{expenses,activity,reports,dashboard}.ts` are the typed clients. `web/src/components/HeatmapGrid.tsx` is the one shared heatmap (a plain CSS grid, no library), used by both `Activity.tsx` and `Reports.tsx`'s Sales tab. `Expenses.tsx` (offline-first recording, inline category creation, an Owner-only history section with reversal) and `Activity.tsx` (heatmap + actor/type/day-filtered feed) are new pages; `Reports.tsx` is a six-tab page (Sales/Products/Staff/Expenses/Stock/Outstanding) reusing the existing `GET /bills?status=outstanding` call for its Outstanding tab rather than adding a new one. `Dashboard.tsx` now makes one `GET /dashboard` call instead of three, shows a real alerts count and items-sold/today's-expenses figures, and the previously-static "Expenses/Reports/Activity" More-menu rows (placeholder text since before this phase) are now real links — Reports/Activity gated to Owners client-side (`isOwner`, matching `Tabs.tsx`'s established pattern) since both need Owner-only capabilities server-side anyway; Expenses is open to both roles since Staff can record. Full `tsc -b`/`eslint --max-warnings 0`/`prettier --check`/`vitest run`/`vite build` all pass.
- **Known gap, matching this codebase's own established precedent** (the Walk-in selling section's caveat for `Sell.tsx`/`salesSync.ts`, and Phase 7's identical note for its own offline UI): the new offline-queueing path in `Expenses.tsx`/`expensesSync.ts` was not driven through a real browser session as part of this pass — only the backend it talks to was live-verified, and the frontend was verified through the full static/unit-test/build check suite, not an interactive or Playwright pass. No new component/unit tests were added for the six new frontend files either (`HeatmapGrid.tsx`, `Expenses.tsx`, `Activity.tsx`, `Reports.tsx`, the rewired `Dashboard.tsx`, and the four new API clients) — existing tests all still pass, but nothing new exercises these specifically. Worth a manual or Playwright pass, and some component coverage, before trusting this in production.
