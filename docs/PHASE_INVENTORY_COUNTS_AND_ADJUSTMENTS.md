## 2. Schema (new migration)

Following this codebase's established "narrow, purpose-built table" pattern (`sale_reviews` over the generic `review_cases` `docs/ARCHITECTURE.md` sketches) rather than building the fully generic version:

- **`stock_counts`** — header: `business_id`, `location_id`, `counted_by`, `idempotency_key` (client-generated, business-scoped unique — same precedent as `sales.idempotency_key`, needed because this can be submitted after a stretch offline, see §4), `started_at` (informational: when the counter actually walked the shelf, not used for staleness logic — see below), `created_at` (server receipt time).
- **`stock_count_lines`** — one row per counted variant: `expected_quantity` (what the counter's device believed the balance was, from a live fetch or from `catalogueCache` if offline), `physical_quantity` (what they counted), `variance` (computed, `physical - expected`), `is_stale` (set once, at server processing time — see below).
- **`inventory_adjustment_requests`** — `business_id`, `location_id`, `variant_id`, `requested_by`, `idempotency_key` (same reasoning as above), `quantity_delta` (signed), `reason_category` (`CHECK IN ('complimentary', 'broken', 'spoiled', 'staff_use', 'manual', 'count_correction')`), `reason_note` (required), `source_count_line_id` (nullable FK, set when a request came from a non-stale count line), `status` (`pending`/`approved`/`rejected`), `approved_by`, `approved_at`, `resolution_note`.
- **`inventory_reviews`** — mirrors `sale_reviews`: `id`, `business_id`, `type` (`CHECK IN ('negative_inventory', 'stale_stock_count')`), `variant_id`, `location_id`, `related_movement_id` (nullable, set for `negative_inventory`), `related_count_line_id` (nullable, set for `stale_stock_count`), `status` (`open`/`resolved`), `resolved_by`, `resolved_note`, `resolved_at`, `created_at`. Same RLS/tenant-isolation pattern every other table here uses.

## 3. Backend behavior

- **Negative-inventory detection.** `internal/sales` already writes directly to `inventory_movements`/`inventory_balances` in its own transaction (it shares the generated sqlc queries with `internal/inventory` directly rather than calling its `Service` methods — an established pattern, not a new one). This phase adds one check there: after a sale-driven movement, if the resulting balance is negative, insert an `inventory_reviews` row (`type='negative_inventory'`). **Automatic only** — there's no staff-initiated "I think we're short" path; a human noticing a discrepancy submits a count instead, which is the mechanism designed for exactly that.
- **Physical counts — staleness is a value comparison, not a timestamp comparison.** A count line submits `expected_quantity` (what the device believed) and `physical_quantity` (what was counted). At processing time the server reads the **live** `inventory_balances` for that variant: if it matches the submitted `expected_quantity`, nothing happened in between — the variance becomes a `pending` `inventory_adjustment_requests` row (`reason_category='count_correction'`, `source_count_line_id` set). If it *doesn't* match, something moved (a sale, a receipt, another adjustment) since the device captured its belief — mark that line `is_stale` and open an `inventory_reviews` row (`type='stale_stock_count'`) instead of guessing. This is what makes the design correct for both a live online count and one that sat queued offline for hours: there's no reliance on comparing an untrusted device clock against a server clock (`docs/ARCHITECTURE.md` §10.2's "do not use client timestamps to establish canonical ordering," applied here even though this isn't the sync protocol) — only "does the server's current truth match what the device thought was true," checked once, at the moment it actually lands.
- **Adjustment requests and approval.** Any signed quantity delta with a required `reason_category` and `reason_note`. Staff can submit (`inventory:adjustment_request`); only Owner can approve or reject (`inventory:adjustment_approve`). Approving posts the real `inventory_movement` (`inventory_events.type='adjustment'`) and updates `inventory_balances` in the same transaction as marking the request approved; rejecting just marks it rejected, no movement ever posts. Complimentary/broken/spoiled/staff-use consumption goes through this exact same pipeline (confirmed) — the `reason_category` enum is what makes "what happened" unambiguous and queryable, not a separate mechanism.
- **Stock history** (closing the "have a place to record that but clearly stating what happened" ask): a new read endpoint returning a flat, chronological feed of `inventory_movements` per variant, each joined to its `inventory_events.type` and, for adjustments, the linked `inventory_adjustment_requests.reason_category`/`reason_note`/who-approved — so the log reads "Receipt: +48 (4 crates)," "Sale: −1," "Adjustment: −2 · Complimentary — given to the inspector (approved by Ada)," not just a signed number.
- **Reviews capability**: `inventory_reviews` uses the already-defined-but-currently-unused `reviews:read`/`reviews:resolve` capabilities rather than borrowing `activity:read`/`sales:reverse` the way `sale_reviews` does — giving those constants their first real purpose.

## 4. Offline support (confirmed: real, not online-only)

Both count submission and adjustment-request submission get genuine offline queueing, matching `Sell.tsx`'s IndexedDB-first precedent rather than `Tabs.tsx`'s online-only one — this is what the capability model's `offlineSafeCapabilities` entry was already anticipating.

- Two new Dexie tables (`web/src/lib/db.ts`, next version bump): `pendingStockCounts` and `pendingAdjustmentRequests`, keyed by `idempotencyKey`, same shape/status lifecycle as `pendingSales`.
- **`expected_quantity` for an offline count comes from `catalogueCache`** (built last phase for Quick Sell's own offline fallback) — no new local caching mechanism needed; a device that's been offline since its last `GET /products` already has a last-known stock figure sitting right there.
- A new `inventorySync.ts` (mirroring `salesSync.ts`'s `flushPendingSales`) posts queued counts/adjustment requests oldest-first on reconnect, stopping at the first failure rather than reordering.
- Writing to IndexedDB happens *before* any network call, same "this is what makes it true offline" rule `Sell.tsx` already established — a count or adjustment request is "saved" the moment it's queued locally, not when the server eventually sees it.

## 5. Frontend

- `Stock.tsx` gains a count-entry flow (pick a variant, enter physical quantity, see the computed variance before confirming) and a staff-facing adjustment-request form (reason category + note + quantity) — both queue offline-first per §4.
- **`Reviews.tsx` becomes the one page for "things needing the owner's attention"**, gaining a second section alongside the existing sale reviews: open `inventory_reviews` (negative-inventory, stale-count — resolve with a note, same as today) and pending `inventory_adjustment_requests` (a distinct approve/reject action, not a resolve). One mental model, one place to check, instead of scattering owner-facing queues across pages.
- New stock history view (variant-scoped log, see §3) — reachable from `Stock.tsx`.

## 6. Explicitly out of scope

- FIFO/COGS allocation (a separate, later costing decision per `docs/ARCHITECTURE.md` §8.5, not required by Phase 7 itself).
- Multi-location UI (schema already carries `location_id` everywhere; no UI exposes it, same as stock receiving).
- Low-stock alerts / reorder thresholds (not in `docs/IMPLEMENTATION_PLAN.md`'s Phase 7 task list; Dashboard's "Stock alerts" stays mock).

## 7. Confirmed decisions (for the record)

1. Complimentary/broken/spoiled/staff-use consumption shares the adjustment-request pipeline; `reason_category` plus the new stock-history view is what keeps "what happened" clearly recorded, not a second mechanism.
2. The owner approval/review queue lives in `Reviews.tsx`, extended with an inventory-reviews section and a pending-adjustments section, rather than a new page.
3. Negative-inventory reviews are automatic/system-detected only.
4. Counts and adjustment requests get real offline queueing (IndexedDB-first, synced on reconnect), reusing `catalogueCache` for the offline "expected quantity" figure.

## 8. Implementation notes

Built exactly to the design above, migration `000022_inventory_counts_and_adjustments`. One schema deviation from §2's sketch: `inventory_adjustment_requests`' decision columns ended up named `decided_by`/`decided_at` (not `approved_by`/`approved_at`) since the same pair of columns is written on both the approve and reject paths — naming them "approved" would have been misleading on a rejection.

- **Backend** (`internal/inventory`: `model.go`, `errors.go`, `convert.go`, `service.go`; `internal/httpapi/inventory_counts_handlers.go`; `internal/sales/service.go`'s `postSaleRound`) implements every piece in §3 exactly as specified — `SubmitStockCount`, `RequestAdjustment`, `ApproveAdjustmentRequest`/`RejectAdjustmentRequest`, `ListOpenReviews`/`ResolveReview`, `GetHistory`, plus the negative-inventory check added directly inside `internal/sales`' own movement-posting code (not a cross-package call, per this codebase's package-boundary convention — see the Stock receiving section's `internal/inventory` "does not depend on" note). 15 new domain-layer tests plus 1 new `internal/sales` test, all passing against real Postgres; `make check` clean.
- **Live-verified end-to-end against an isolated backend instance** (never the developer's own dev port), using the frontend's own exact request/response shapes over curl: a stock count with a correct `expected_quantity` and a variance auto-created a `pending` `count_correction` adjustment request (not a review); approving it posted a real movement and updated the balance; a count with a *stale* `expected_quantity` set `is_stale=true` and opened a `stale_stock_count` review instead, with **no** adjustment request created; idempotent replay of the same count returned the identical result with no duplicate side effects; a direct client request for `reason_category=count_correction` was rejected by validation (server-side, matching the frontend's own `Exclude<..., 'count_correction'>` type); rejecting an adjustment request posted no movement and left the balance unchanged; an adjustment approved past a variant's balance into negative territory opened a `negative_inventory` review, and separately, a walk-in sale that oversold an already-negative variant opened its own `negative_inventory` review too — confirming the shared design works correctly from both entry points (`internal/inventory` and `internal/sales`) without any code shared between the two beyond the generated sqlc layer; stock history returned a correct chronological feed (receipt → count-correction adjustment → staff-use adjustment → sale) with reason/decider context on every adjustment row; and the Staff/Owner permission split held exactly as designed (Staff: 201 on submitting a count and requesting an adjustment, 403 on listing/approving/rejecting). All test data cleaned up afterward via the RLS-aware `SET LOCAL ROLE jbm_app` transaction pattern.
- **Frontend**: `web/src/lib/db.ts` gained `pendingStockCounts`/`pendingAdjustmentRequests` (Dexie version 4); `web/src/lib/inventorySync.ts` mirrors `salesSync.ts`'s `flushPendingSales` exactly, as two independent queues (a count and an adjustment request post to different endpoints and don't depend on each other's sync state); `web/src/api/inventory.ts` and `web/src/api/reviews.ts` gained the typed clients for every new endpoint. `Stock.tsx` gained a three-way mode switcher (Restock/Count/Report issue) — Count and Report-issue share a `VariantPicker` sub-component (search + pick from the already-loaded catalogue, with a "History" action per row) that neither needs the Restock flow's catalogue-template or custom-product paths, since both only ever act on a product that already exists; both write to IndexedDB before any network call, exactly like `Sell.tsx`'s `completeSale`, and attempt an immediate flush when online. A history modal (variant-scoped, reachable from either picker) renders `GET .../history`'s feed with human-readable event/reason labels. `Reviews.tsx` gained two new sections above the existing sale-reviews one: a pending-adjustments queue (approve/reject, refreshing the inventory-reviews list afterward since an approval can itself open one) and an inventory-reviews queue (resolve, same interaction shape as sale reviews). Full `tsc -b`/`eslint --max-warnings 0`/`prettier --check`/`vitest run`/`vite build` all pass on every file touched this phase.
- **Known gap, matching this codebase's own established precedent for exactly this situation** (see the Walk-in selling section's identical caveat for `Sell.tsx`/`salesSync.ts`, and the OAuth section's for its frontend): the new offline-queueing paths in `Stock.tsx`/`inventorySync.ts` were not driven through a real browser session as part of this pass — only the backend they talk to was live-verified, and the frontend was verified through the full static/unit-test/build check suite, not an interactive or Playwright pass. Worth a manual or Playwright pass (submit a count/adjustment while offline in DevTools, confirm it queues and later flushes) before trusting this in production.
