# Phase 6 — Flexible tabs, named credit, and payments

**Status:** Approved and built — backend (`internal/sales`'s tab/table/customer/payment methods, migration `000020`) and the real `/dashboard/tabs` frontend are live and verified end-to-end against a running backend, including the Staff/Owner capability split. The frontend here is deliberately **online-only** — see "What's different from Phase 5" below.
**Depends on:** `internal/sales`'s existing Phase 5 walk-in-selling foundation (`bills`, `sales`, `sale_items`, `payments`) — this phase widens that schema and service rather than replacing it.
**Deviates from:** `docs/IMPLEMENTATION_PLAN.md`'s frozen phase order, the same way `docs/PHASE_STOCK_RECEIVING.md` and `docs/PHASE_WALKIN_SELLING.md` do — Phase 6 is specified as depending on Phase 4 ("sync foundation"). Phase 4 is deferred until invitations bring a second device into a real business (see project memory `phase4-sync-foundation-deferred`). This was an explicit, reconfirmed decision at the start of this phase: asked directly whether to build Phase 4 first, the answer was to keep deferring it and build Phase 6 now, single-device, the same way Phase 5 did.

## What "single-device slice" means concretely here

- **In scope:** table labels, lightweight named customers, opening a tab against either (or neither, for a walk-in tab opened ahead of its first round), appending multiple immutable sale rounds to an open tab, partial payments with overpayment rejected, payment reversal, owner-only reasoned debt write-off, and the `open → closed_unpaid → settled` / `void` status machine.
- **Out of scope, deliberately:** the generic multi-purpose `review_cases` system Phase 4 describes, any multi-device conflict resolution, and — see below — offline queuing for any of this phase's actions.

## What's different from Phase 5's offline story

Phase 5's `Sell.tsx` writes every completed sale to IndexedDB *before* any network call, so "sale recorded" is true even fully offline, then syncs on reconnect. Tabs deliberately don't get that treatment in this pass: a tab is a long-lived object touched by several separate operations over time (open, several rounds, several payments, a close, maybe a write-off) rather than one atomic "record this and you're done" action, and building a correct multi-step offline outbox for that shape is real work that overlaps heavily with what Phase 4 already exists to solve properly. `Tabs.tsx` calls the API directly and shows a plain "you're offline, actions won't go through" banner (via the existing `useConnectivity` hook) rather than silently queuing writes it can't yet safely reconcile. This is a real, deliberate scope narrowing — not an oversight — and it's the first concrete case where deferring Phase 4 has an actual, felt cost instead of a hypothetical one. Revisit this specifically (not just Phase 4 in general) once a second device is real.

## Schema (migration `000020`, building on `000019`)

- **`tables`** — business-configured labels (T1–T5 style), unique per business. No kitchen/routing behavior.
- **`customers`** — `name` is `NOT NULL` on the row itself. The "optional" part of customer identity (`docs/ARCHITECTURE.md` §8.3) is whether a *bill* references one at all, not whether a customer record can be created nameless.
- **`bills`** widens: `status` CHECK now allows `closed_unpaid`/`void` alongside `open`/`settled`; new nullable `table_id`/`customer_id`; new `balance_kobo`, a rebuildable projection (every existing Phase 5 row defaults to `0`, which is factually correct — every one of them is an already-settled, fully-paid walk-in sale).
- **`bill_write_offs`** — owner-only, reasoned, immutable. Never a payment (no money changes hands); kept separate from `payments` so that table stays "actual money movement only."
- **`payments`** needed no schema change — it was already `bill_id`-scoped (not `sale_id`-scoped), which is what makes many payments against one bill a natural fit rather than a redesign.

## The two production rules this phase encodes

1. **`balance_kobo` is a rebuildable projection, never itself the source of truth.** It's always `sum(sales.total_kobo) − sum(payments.amount_kobo) − sum(bill_write_offs.amount_kobo)` for that bill — the same "immutable movements + materialized state" pattern as `inventory_balances`. `internal/sales.recomputeBillBalance` is the one place this is computed and persisted, called by every bill-mutating method while still holding that bill's row lock.
2. **A bill's status machine is driven by balance, not by which action was last taken.** `open` never auto-transitions (a tab can sit at a zero balance and keep taking rounds); `closed_unpaid` becomes `settled` the moment balance reaches zero, from a payment *or* a write-off; a `settled` bill reverts to `closed_unpaid` if a payment reversal makes its balance nonzero again. `void` is terminal and only reachable when net sales and balance are both already zero — voiding is for discarding a tab that never became real, not a way to erase real unpaid activity.

## Backend

- **`internal/sales.postSaleRound`** is the resolve-and-post-items-and-inventory core extracted out of Phase 5's `CreateSale` — shared verbatim by `CreateSale` (walk-in: wraps a new bill and an immediate payment around it) and the new `AddSaleRound` (appends to an already-open tab, no bill or payment created). Refactoring this out, rather than duplicating it, is what makes "more items create another immutable sale round on the bill" (`docs/IMPLEMENTATION_PLAN.md` Phase 6) share every staleness-review/inventory-deduction rule Phase 5 already established, instead of re-deriving them.
- **Every bill-mutating method (`AddSaleRound`, `CloseBill`, `RecordPayment`, `ReversePayment`, `WriteOffBill`, `VoidBill`) takes the bill row lock first** (`SELECT ... FOR UPDATE` via `GetBillForUpdate`) before reading or changing its balance — this is the concrete case `docs/IMPLEMENTATION_PLAN.md`'s explicit "Add tests for concurrent payment/bill locking" acceptance criterion exists for. `TestConcurrentPaymentsNeverExceedBalance` (`internal/sales/tabs_test.go`) exercises this directly with two goroutines racing to pay off the same bill: the row lock serializes them, so the loser sees the winner's already-applied balance and is rejected as an overpayment — never both succeeding and leaving the bill overpaid.
- **`CloseBill` is the enforcement point for "a customer name is mandatory whenever credit/outstanding debt is recorded."** It rejects closing with a nonzero balance unless the bill already has a `customer_id` attached — and since `customers.name` is `NOT NULL`, attaching one at all satisfies the naming requirement; there's no separate "name is present" check needed.
- **`WriteOffBill` only accepts a `closed_unpaid` bill**, not a still-`open` one — a tab is written off only after it has stopped taking rounds, keeping the status machine linear rather than allowing a write-off to interleave with more items still being added.
- **Capabilities were already fully anticipated** in `internal/tenancy/capabilities.go` before this phase touched any HTTP code — `bills:read`/`bills:manage`/`bills:write_off`, `credit:grant`, `payments:record`/`payments:reverse` all already existed with the exact Owner/Staff split this phase needed (Staff has everything except `payments:reverse` and `bills:write_off`). Wiring the routes to them was the only new work; the permission design itself predates this phase.
- **Verified live end-to-end** against a running backend: opened a table tab, added two rounds, partial-paid, confirmed closing without a customer is rejected (`409`), paid off the rest, confirmed closing then settles directly; opened a customer credit tab, closed it with a real balance (allowed, since a customer was attached), write-off validation (empty reason rejected) and a full write-off settling it; voided a clean empty walk-in tab; and confirmed a Staff session can open/round/pay/close but gets `403` on both write-off and void. Test data cleaned up afterward. A pre-existing test-cleanup ordering bug in `internal/sales/service_test.go` (deleting `sales` before `inventory_events`, whose `sale_id` foreign key — added by Phase 5's own migration — blocks that order) was found and fixed as part of this work; it had been silently leaking every sales test's rows since Phase 5, not something newly introduced here.

## Frontend

- **`Tabs.tsx`** (`/dashboard/tabs`, replacing the dead `#bills` anchor `AppBottomNav` had reserved) — a persistent tab-switcher strip (every open bill one tap away, wraps onto additional lines rather than scrolling off-screen) with the selected bill's detail below: a live, editable "current order" (see below), payment history, a payment input, close/void, and an owner-only write-off panel gated on `useSession().memberships`' role for that business. `AppBottomNav`'s "Bills" tab points here and highlights via the same `pathname.startsWith` pattern the other tabs use.
- **`src/components/ProductGrid.tsx`** and **`src/components/CartPanel.tsx`** are the search/tap-to-add grid and bottom cart sheet, extracted out of `Sell.tsx` so Quick Sell and "add/adjust this tab's order" render the literal same component rather than two hand-kept-in-sync copies.
- **`src/api/tabs.ts`** is the typed client, same snake_case-to-camelCase boundary convention as `src/api/sales.ts`/`src/api/catalogue.ts`.
- Client-side role gating (hiding write-off/void buttons from Staff) is a UX nicety only — the real enforcement is server-side capability checks, verified live above.

## Editable orders (polish pass, 2026-09-17)

The first cut showed each round as its own frozen timestamped card with no way to fix a mistake short of a full sale reversal. Confirmed with the user before building: minor item corrections (add one more, remove one added by mistake) should be a normal staff action as long as the bill hasn't been paid in full yet; once **settled or void**, a correction has to go through the heavier, owner-only route instead.

- **`Service.RemoveBillItem`** (`internal/sales/tabs.go`) is the new half of this: posts a compensating *negative*-quantity round for one variant, capped so you can never remove more than is currently net-present on the bill (`SumBillItemQuantityByVariant`), restocking inventory the same way `ReverseSale` already does. Never edits or deletes a previously posted round — this is item-level correction, not a rewrite of history. `AddSaleRound` (the existing "+" half) was widened from open-only to open **or** `closed_unpaid`, matching the same boundary.
- **The boundary is `ErrBillNotEditable`**: allowed on `open`/`closed_unpaid`, rejected on `settled`/`void`. Verified live in both directions, including that a `closed_unpaid` bill (partially paid, balance remaining) still accepts both an add and a remove.
- **Frontend**: `Tabs.tsx` no longer builds a local draft cart that gets submitted as one batch. `currentOrderLines` is computed by netting quantities across every round already on the bill (a removal's negative quantity cancels against the rounds that added it), rendered via `CartPanel` with a live +/- stepper — each tap posts immediately (`handleAdjustQuantity`), no separate "confirm" step. The round-by-round timeline survives underneath as a secondary "ROUNDS" history, with negative-total rounds labeled "Correction" so the audit trail stays legible rather than reading as a data error.
- **Deliberately not built yet: reversing an individual round on a *settled* bill.** `ReverseSale` (Phase 5) always opens a brand-new, disconnected bill for the compensation — correct for a one-shot walk-in sale, but wrong here, since a tab's rounds share one ongoing bill; reusing it as-is would silently credit the wrong bill and leave the tab's balance not reflecting reality. Worse, reversing a round on an *already fully paid* bill can legitimately produce a negative balance (money owed back to the customer), which needs real refund-handling design, not just a status flip. Rather than ship a half-correct version of "that review route" the user asked for, this is left as a named follow-up — see the money-back-refund-shape problem above before building it.

### Bug found and fixed the same day: removal after full payment produced a negative balance

An `open` bill deliberately never auto-settles just because its balance hits zero — a tab can sit at zero and still take more rounds later (pay-as-you-go). But the first cut of `RemoveBillItem` only checked bill *status* (open/closed_unpaid), not whether the money had already been collected — so a bill paid in full while still `open` stayed fully editable, and removing an item afterward silently produced a negative "due" amount (a refund owed, displayed as confusing UI: "₦-3,300 due"), caught live by the user clicking through a real tab.

**Fix**: `RemoveBillItem` now rejects (`ErrBillFullyPaid`, `409`) when the removal's amount would exceed what's still outstanding — checked as `quantity × unitPriceKobo > bill.BalanceKobo`, not a blunt `balance <= 0` test. That distinction matters: a bill can also reach zero balance purely because net quantity nets to zero with no real payment involved (e.g. add 3, remove all 3) — in that case there's nothing left to remove anyway, so the pre-existing quantity-sufficiency check (`ErrInsufficientQuantityOnBill`) fires first and is the more accurate/specific error; the fully-paid check only matters once real money is involved. `AddSaleRound` is unaffected — adding only ever increases what's owed, so it stays valid at any balance, preserving pay-as-you-go. `TestRemoveBillItemRejectsOnceFullyPaid` (`internal/sales/tabs_test.go`) reproduces the exact scenario and confirms adding still works afterward. Verified live against a running backend.

## Explicitly out of scope

- Offline queuing for any tab action (see "What's different from Phase 5" above) — this is the one deliberate regression from this codebase's usual offline-first bar, tracked as a named follow-up rather than silently accepted.
- Multi-device sync, conflict resolution (Phase 4, still deferred).
- A UI for browsing customers independently of opening a tab against one, or editing/deactivating a table (both exist server-side via `CreateTable`/`CreateCustomer`/`ListTables`/`ListCustomers`, no settings screen consumes the update path since there isn't one yet).
- Reminders to customers carrying a balance (`docs/ARCHITECTURE.md` §8.3 mentions phone/email "should be encouraged... for sending reminders" — no sending mechanism exists).
